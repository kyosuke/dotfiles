# Codex を動かす

委任のたびに読む。ここに置くのはランナーに依らない Codex 側の運用で、依頼文の渡し方、承認の境界、待機中の判断、worktree での並列化、報告回収の制約、ネットワークの開け方、スレッドの分割と片付けを扱う。ランナーごとのコマンドは `runner-herdr.md`・`runner-orca.md`（使っているものだけ）、詰まったときの復旧は `recovery.md`、実測の詳細は `evidence.md`。

ランナーの操作（起動、発注、状態の読み方、報告の取り方）はそちらの出典に従い、想像で補わない。

## 起動時に決めること

- **プロファイルの値を明示する。** モデル・推論量・Fast は毎回渡し、`~/.codex/config.toml` の既定に落とさない。渡し方はランナーの reference。
- ファイル変更にフラグは要らない。`workspace-write` で既定で書ける。調査だけを頼むなら読み取り専用（`-s read-only`）で起動する。
- ネットワークやループバックを要する検証が発注に含まれるなら開ける（下記）。
- 承認方針は既定の `on-request` のまま起動する。`-a untrusted` は trusted 集合（`ls`・`cat`・`sed` など）の外にあるコマンドをすべて承認へ上げる（`find` も対象になった）。ディレクターは承認できないので、そのセッションでは作業が進まない。
- モデル名・推論量・オプションが記述と食い違ったら、想像で補わず `codex --help`・`~/.codex/models_cache.json`・ランナーのヘルプで実際を確認する。

## 依頼文を渡す

依頼文は Write ツールでファイルへ書いてから渡す。発注文は検収と差し戻しの基準になるので、差し戻し文と並べて読み返せる形で残す。

シェル経由で渡すので、ヒアドキュメントも直接埋め込みも使わない。文中のバックティックがコマンド置換として実行され、その部分が依頼文から消える（実運用で `` `wrangler dev` `` が起動してサーバーとして残り、仕様の核が欠落した依頼文が渡った）。サンドボックスや権限に触れる文言を含むヒアドキュメントは Claude Code の classifier に止められることもある。

## 完了を待つ

完了の判定はランナーが返す状態か完了通知で行い、自分でポーリングしない。承認待ちで止まったら「承認を求められたとき」へ。

所要時間は、読み取りだけの小さな依頼で12〜40秒。実装を伴う依頼は20分を超えることがある。ランナーの待機コマンドを Bash で回すなら、上限が10分なので `run_in_background: true` で投げ、完了通知を受けてから読む。

- **ファイルが未変更でも失敗と判断しない。** Codex は数分から十数分を調査に使ってから書き始める（実運用では開始3分後はまだ調査中だった）。
- 完了通知を受け取る前に、検収と最終報告を終えない。
- 待機中は同じ作業ツリーを触らない。**書き込みを伴う委任を同一作業ツリーで並列実行しない。** 画面やエージェントを分けても作業ツリーは共有されるので、表示の分離は並列化の根拠にならない。書かせる並列化には worktree を使う（下記）。
- 読み取りだけの委任（読み取り専用で起動した調査・レビュー）は同じ作業ツリーで並走してよい。互いの結果を突き合わせたい調査は、むしろ分けて同時に走らせる。

## worktree で並列に走らせる

書き込みを伴う委任を同時に出すなら、1本ごとに worktree を作り、そこで Codex を起動する。作り方と消し方はランナーの公式の手順に従う（`runner-herdr.md`・`runner-orca.md`）。`git worktree add` を直接叩かない。ランナーが worktree として認識せず、ペインやターミナルとの対応も片付けも効かなくなる。

**分けてよいのは、次をすべて満たすときに限る。**

- 書き込みを伴う委任が2本以上ある
- 互いに触るファイルが重ならない。同じファイルや同じ生成物（lockfile、スナップショット、生成型）を書く見込みがあるなら、取り込みで衝突する
- 片方の結果を待たずに依頼文を書き切れる。順序に依存するなら、同じ作業ツリーで順に出す

数分で終わる小さな修正は分けない。worktree の準備（下記の依存物）と取り込みの手間のほうが大きい。読み取りだけの委任は、読み取り専用で起動すれば同じ作業ツリーで並走できるので、分けなくてよい。

**worktree はコミット済みの状態から始まる。** 元の作業ツリーにある未コミットの変更は入らない。Orca は起点を指定しないと repo の既定ブランチから作るので、今いるブランチ以外から始まることもある（2026-10-01 実測）。起点は毎回明示する。未コミットの変更が前提になる作業なら、`git diff --binary` を worktree へ `git apply` で持ち込んでから発注するか、分けずに元の作業ツリーで出す。

**追跡されていないファイルも入らない。** `node_modules` などの依存物と、`.env` などの秘密情報が無い。依存物のインストールはネットワークが要るので、起動時に開け（下記）、インストールのコマンドを依頼文の `<verification>` の前に書く。秘密情報は worktree へ複製しない。それが無いと検査が走らないなら、その作業は分けずに元の作業ツリーで出す。

**依頼文の `<context>` には worktree のパスを書く。** Codex の作業ディレクトリと書き込める範囲はそこになるので、元の作業ツリーのパスは書かない。

**検収は worktree の中で行う。** `git -C <worktree> status`・`git -C <worktree> diff` で読む（`review.md` の手順はパスを読み替えればそのまま使える）。新規ファイルは `git -C <worktree> add -N .` で intent-to-add にしてから diff を取る。こうしないと diff に載らない。

**合格したものだけを元の作業ツリーへ取り込む。** コミットはしない（`../SKILL.md` の基本規則）。

```bash
git -C <worktree> add -N .
git -C <worktree> diff --binary > <scratchpad>/<タスク名>.patch
git apply --check <scratchpad>/<タスク名>.patch && git apply <scratchpad>/<タスク名>.patch
```

`--check` が通らなければ取り込まない。衝突を自分で解かず、どの worktree の差分がどこで当たったかをユーザーへ報告する。元の作業ツリーで、取り込み済みの状態を前提に Codex へ出し直すのが基本になる。取り込んだあとは、元の作業ツリーで検査をもう一度走らせる。別々に合格した変更どうしが、合わさると壊れることがある。

**中身を見ないまま強制オプション（`--force`）で消さない。** パッチの取り損ね、取り込み後に Codex が足した変更、別のタスクの worktree との取り違えは、強制で消した時点で戻せなくなる。消し方はランナーの reference にあり、まず強制なしで消す。変更が残っていない worktree（読み取りだけで終わった、何も書かずに落ちた）はそれで消える。自分が作ったものだけを消す。

変更が残っていて拒まれたら、消す前に中身を確かめる。

```bash
git -C <worktree> add -N .
git -C <worktree> status --short
git -C <worktree> diff --binary > <scratchpad>/<タスク名>-remaining.patch
git apply --reverse --check <scratchpad>/<タスク名>-remaining.patch   # 元の作業ツリーで実行
```

確かめた結果で次のように分ける。

| 残っている変更 | 判断 |
|---|---|
| 取り込んだ差分と同じ（上の `--reverse --check` が通る。元の作業ツリーに全部入っている） | 不要。消してよい |
| 依頼の成果物でないことが中身から明らかなもの（ビルド成果物、キャッシュ、Codex が試しに作って捨てたファイル） | 不要。消してよい |
| 取り込んでいない成果物の一部、意図の読めない変更、別のタスクのものに見える変更 | 消さない。パス、ブランチ、該当ファイル、何が分からないかを添えてユーザーに諮る |

不要と判断したときだけ、その worktree に限って強制で消す。直前に `status --short` をもう一度見て、判断したときから増えていないことを確かめる。何をどう判断して消したかは最終報告に書く。判断の材料にしたパッチは `<scratchpad>` に残しておく。

## 報告を回収する

回収できたのは実測で200行台なので、これを超える報告は分割して依頼する。

**終端マーカーを依頼文に入れない。** 完了の検知はランナーの仕事で、待機コマンドが状態として返すので判定が二重になる。取りこぼしの検出にも使えない。画面から読むランナーでは下端が基準なので、失われるのは先頭である。機械的に判定したいならマーカーは報告の**先頭**へ置く。

**画面の記録は証拠ではない。** 見えているのは Codex が描いた画面であり、コマンドの生出力ではない。Codex はツール出力を `… +464 lines` のように畳むので、畳まれた部分は読めない。報告と画面が食い違ったら、どちらも信じずに、出力が短くなる形で追試させる（実害の記録は `evidence.md`）。実行ログの中身も Codex の内部状態であって成果物ではない。検収は画面でもログでもなく `git diff` で行う（`review.md`）。

## 承認を求められたとき

止まったら、ランナーから何を聞かれているかを読む。

**ディレクターは承認を代行しない。** Claude Code の classifier が承認の代理入力を止める。実際に止められたのは、承認プロンプトへキー入力で承認を送る操作と、権限昇格の文言を含むヒアドキュメントである。Codex へ「ネットワークが要るコマンドは昇格を要求してよい」と依頼文で許すのは、承認の代行ではないので止まらない。

却下は通る。実測では却下したファイルは作られなかった。承認が必要な場面は、見えている画面でユーザーが答える。ディレクターは何を求められているかをユーザーへ伝えて待つ。

却下した直後は Codex が「どうするか指示して」で待つため、状態は承認待ちのままに見える。通常の発注を送ると進む。

**すべての承認が人まで来るとは限らない。** `auto-review` モードでは `approvals_reviewer: auto_review` が効き、`on-request` の承認のうち対象になるものは auto-reviewer のサブエージェントが処理する。**権限の昇格は auto-reviewer に任せる。** 承認を人へ上げ直す設定変更は提案しない。危険な操作はそこで弾かれる前提で運用し、止まらずに進んだことを承認が不要だった証拠として読まない。何が自動で通ったかは差分で確かめる（`review.md`）。

## ネットワークとローカルバインド

Codex の `workspace-write` サンドボックスは既定でネットワークを閉じる。macOS の Seatbelt が `127.0.0.1` への bind まで拒否するため、`@cloudflare/vitest-pool-workers` の workers プール（workerd がループバックを listen する）と `wrangler dev` が動かない。失敗の見え方が厄介で、vitest は起動できたプールの件数だけを passed として表示するので、workers プールが落ちても「Tests 36 passed」と出る。Codex はこれを成功として報告した。

**起動時に `-c sandbox_workspace_write.network_access=true` を渡して開ける**（herdr・Orca 共通。`runner-herdr.md`・`runner-orca.md`）。開くのはそのセッションのネットワークだけで、書き込みは作業ツリーのままである。

**`--mode full-access` を使わない。** このモードは `approval_policy: never` と `sandbox_mode: danger-full-access` をまとめて当て、ネットワークだけでなく作業ツリー外への書き込みまで開き、承認の判断が一度も入らなくなる。ネットワークが要るだけなら上の起動引数で足りる。

**`~/.codex/config.toml` へは書かない。** グローバルなので全 Codex 実行（TUI 含む、クライアント案件のリポジトリ含む）で外向きが開き、戻し忘れがそのまま恒久設定になる。

運用は次のとおり。

- ネットワークやループバックを要する検証（workers プール、`wrangler dev`、外部APIを叩く取得、`wrangler --remote`）が発注に含まれるなら開ける。これは都度の確認を要しない。開けないまま出すと、Codex は一度も実行できないテストを論理だけで書くことになり、差し戻しが増える。
- 要らない発注では開けない。実装とサンドボックス内で完結する検査までを委任する形を崩さない。
- 開けられないことを理由にプロファイルを上げない。昇格が通ったことを「安全だった証拠」として読まない。
- 開けた事実（起動引数）は報告に書かせ、検収で確かめる（`review.md`）。
- 開けなかった発注では、`<verification>` にサンドボックスで完走するコマンドだけを書き、フルスイートはディレクター側で実行すると明記する（`ordering.md`）。

開けている間の代償は外向き通信にある。リポジトリ内容や取得ページ経由の prompt injection による持ち出し経路が増え、通信先は制限されない。Codex がコマンド単位の昇格を求めた場合、通ったコマンドはサンドボックス外で全ディスクを読める（1Password でマウント中の `.env` も含む）。起動時オプションはネットワークだけを開くので、こちらを使い、昇格を既定にしない。

## 消費を確かめる

`dev-max` の許可を諮るときや、下げたプロファイルの効果を測るときに使う（`ordering.md`）。取り方はランナーで違う（使っているランナーの reference）。TUI が使えるなら `/status` が適用中のモデル・推論量・週次の残量を返す。ローカルのUIコマンドなのでターンを消費しない。

**画面のフッター表示を推論量の確認に使わない。** `model_reasoning_effort=none` で起動したセッションが、フッターには `gpt-5.6-luna default fast` と出しながら `/status` では `reasoning none` を返した。起動直後のバナーは `/status` と一致する。

## スレッドを分ける判断と片付け

新しい依頼は新しいエージェントで出す（`../SKILL.md`）。同じスレッドへ続けるのは、それまでのやり取りが作業の前提になる場合に限る。

- 検収で見つけた不備の差し戻し
- 直前の変更を踏まえた追加作業で、その調査を引き継ぐほうが速いもの
- 依頼文へ書き写すには大きすぎる文脈（長い調査の結果など）を土台にする作業

迷ったら分ける。判定はその文脈を依頼文へ数行で書けるかで足りる。書けるなら新しいスレッドへ渡す。

差し戻しは同じエージェントへ発注を送るだけで同じスレッドが続く。明示的に再開する操作は要らない。送る前に、そのエージェントが待機状態（承認待ちではない）であることを確認する。承認待ちのまま送ると、返ってきた承認要求が新しいものか直前のものかを区別できない。

終わったら自分が作ったエージェントだけ畳む。放置すると、同一作業ツリーで別の Codex が走る事故が起きる。Codex のセッションID（`/quit` 時に表示される `codex resume <UUID>` と一致する）は、あとで文脈が要ると分かったときの再開に使えるので、長い作業では控えておく（手順は `recovery.md`）。
