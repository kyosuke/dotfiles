# Codex ディレクター

Claude Code は発注・検収・報告を担い、成果物の作成は原則 Codex に委任する。

## 起動する場合・しない場合

判断軸は「コードか文章か」ではなく「Codex への委任とモデル・推論量の選択が価値を生むか」。出力の種類で最初から締め出さない。

- **起動する**: 調査・実装・修正・テスト・レビュー・検証の委任。コード実装のほか、調査や事実確認を伴う文章、デモコードや手順の検証が要る技術文章、コードから生成するドキュメント、多数ファイルの一括編集・移行・翻訳。
- **起動しない（Claude が直接扱う）**: 単なる質問・相談、設計案の比較、調査も検証も伴わない単発の執筆（スタイル重視の記事・エッセイ・提案文）。委任と検証のループがないから直接書くという判断で、作業の途中で調査や検証が生じたら委任を検討する。

## 役割分担

- **ディレクター（Claude）**: 合格ラインと不合格条件の言語化、プロファイルの選択、単体で完結する依頼文、証拠に基づく検収、最終報告。
- **実装AI（Codex）**: コードベースの調査、ファイル変更、テストの追加・修正、formatter・lint・型チェック・テストの実行、変更内容と実行結果と未解決事項の報告。

## ワークフロー

1. **整理**: 目的・制約を把握する。コードベースを見れば分かることは自分で調べる。
2. **合格ラインの確定**: 何を満たせば完了か、何があれば不合格か、どう判定するかを書けるか確かめる。埋まらない項目が残るなら発注せず、ユーザーへ確認する（下記）。
3. **発注設計**: プロファイルを選び、単体で完結する依頼文を組む。`references/ordering.md` を読む。
4. **発注前報告**: 選んだプロファイルと選択理由をユーザーへ短く伝える。基準より1段下げたなら、その根拠と、落ちたときの切り分け方も添える。収集と判断を別の発注へ分けたなら、その分け方も1行で伝える。`dev-max` を選んだなら報告ではなく許可を求め、返事を待ってから発注する。
5. **委任**: `references/execution.md` と、判定したランナーの reference（下記）に従って Codex を呼ぶ。
6. **検収**: `references/review.md` に従い、実際の差分とテストを確認する。
7. **最終報告**: 変更内容、選んだプロファイル、実行した検査、確認した内容、直さずに残した指摘、残る制約・未確認事項をまとめる。

## 合格ラインが埋まらないなら発注しない

Codex が独自の基準で進めないよう、完了・不合格条件と判定手順を渡す。空欄はまずコードベース・既存実装・git 履歴・外部ドキュメントで調べる。

- 目的が複数の読み方を許す（何を優先するか、どこまでを今回の範囲とするか）
- 現状の挙動と期待する挙動のどちらが正か決まらない
- 完了の判定手段が無い（実行して確かめる方法も、見て分かる基準も出せない）

調べても決まらなければ、選択肢と推奨を添えてユーザーに確認し、返事を待つ。差し戻しやプロファイルの引き上げで合格ラインの曖昧さを補わない（`references/ordering.md`）。

## プロファイルから選ぶ

モデルと推論量は、ユーザーが用意したプロファイルから選ぶ。モデルIDと推論量を自分で組み立てない。

| プロファイル | 中身 | 使う場面 |
|---|---|---|
| `dev-low` | `gpt-6-luna` + `low` + Fast | やることが依頼文で一意に決まる作業。収集役 |
| `dev-default` | `gpt-6-luna` + `high` + Fast | 既定。迷ったらここ |
| `dev-high` | `gpt-6.2-sol` + `low` + Fast | 構造の理解が要る、影響範囲が広い、正しさの判定が難しい実装 |
| `dev-xhigh` | `gpt-6.2-sol` + `high` + Fast | `dev-high` で抜けなかったとき。絞り込んだ材料からの判断 |
| `dev-max` | `gpt-6.2-astra` + `xhigh` | `dev-xhigh` でも抜けなかったとき。**毎回ユーザーの許可を取ってから出す** |

この表がプロファイルの定義である。herdr・Orca・exec の reference は起動引数へ展開した表を持つので、プロファイルを変えたら4つとも直す。

承認は全プロファイルで `approvals_reviewer=auto_review` を使い、上書きしない。表から外す判断、プロファイルの選択・引き下げ、`dev-max` の許可に添える材料は `references/ordering.md`。Fast の渡し方はランナーの reference。

## 委任の経路

委任は、**ユーザーから見える場所で Codex を動かすランナー**を通して行う。ランナーへ求めるのは次の4つで、どれかが欠けるなら委任経路として使わない。例外は herdr・Orca が無いときの `codex exec`（下記）だけである。

- 動作がユーザーに見える
- 承認を求められたら人へ届き、その場で答えられる
- 差し戻しが同じスレッドで続く
- 報告を機械的に回収できる

**herdr・Orca があれば、サンドボックスの検証だけでも可視ランナーを使い、`codex exec` は使わない。** `codex exec` の承認待ち対策は `references/runner-exec.md`。次のコマンドでランナーを判定する。

```bash
printf 'HERDR_ENV=%s ORCA_TERMINAL_HANDLE=%s\n' "${HERDR_ENV:-}" "${ORCA_TERMINAL_HANDLE:-}"
[ -n "${ORCA_BOT_TOOLS_TOKEN:-}" ] && echo ORCA_BOT=1   # 値は秘密。有無だけ見る
```

| 判定 | 操作の出典 |
|---|---|
| `HERDR_ENV` が 1 | herdr 公式スキル（Skill ツールの `herdr`、無ければ `herdr --skill`）。この Skill からの上書きは `references/runner-herdr.md` |
| `ORCA_BOT_TOOLS_TOKEN` が空でない（Orca bot） | 自分では委任しない。Claude の worker（`orca orchestration worker-start --agent claude`）を立て、spec に「codex-director で Codex へ委任する」と書く（下記） |
| `ORCA_TERMINAL_HANDLE` が空でない | Orca 本体のガイド（`orca skills get orca-cli`）。この Skill からの上書きは `references/runner-orca.md` |
| どれでもない（Codex アプリ内など） | `references/runner-exec.md`。見えない代替なので、発注前報告でその旨を添える |

上の行から順に判定し、最初に当たった行を使う。Orca のターミナルの中で herdr を動かしているなら、内側のランナーが優先される。

**判定したランナーの reference だけを読む。** 他のランナーは制約も手段も違い、読むと混ざる。

**Orca bot は director にならない。** Orca の bot の規則（コード作業は worker へ渡し、bot 自身は対象リポジトリを見ない）に合わせ、director の役は worker が持つ。dispatch された worker には `ORCA_BOT_TOOLS_TOKEN` が引き継がれず `ORCA_TERMINAL_HANDLE` が入るので、worker の中のこの Skill は `runner-orca.md` の行に当たる。bot が spec に書くのは、目的と合格ライン、この Skill を使うこと、検収をテストの実行だけで済ませず壊れた入力を仕込むなどして確かめること、PR を出すならその指示である。`--item <n>` を付けると bot の item に結び付く（bot の chat から以外は拒否される）。`worker_done` が来たら、bot は報告と PR の差分を抜き取りで確かめてから item へ書く。

毎回 `references/execution.md` に従って起動・発注・待機・報告回収・片付けを行う。詰まったら `references/recovery.md`。

**依頼ごとに新しい Codex を立てる。** 差し戻しなど、過去のやり取りが前提になる場合だけスレッドを継ぐ（`references/execution.md`）。

並列委任をためらわず、書き込みがある場合は公式手順で1本ごとに worktree を分ける（条件と手順は `references/execution.md`）。画面配置はランナーの作法に従う。

## 基本規則

- ディレクター自身は原則コードを変更しない。誤字・format・明白な一行修正のみ自分で直してよい。不備を見つけても直さず、具体的な修正内容を Codex へ依頼する。
- Codex の報告だけを信用せず、必ず実際の差分（`git diff` など）を読む。テストが通った報告ではなく、テストの内容が変更を本当に検証しているかを見る。
- ユーザーが明示的に許可しない限り、コミット・push・デプロイはしない。
- 変更範囲・抽象化・テストの前提は理由ごと依頼文に織り込む（`references/ordering.md`）。
- 修正依頼は2回までを目安にする。上限に達したときの報告項目は `references/review.md`。

## 運用で気づいたことの置き場

再発する制約や失敗は、結論を該当する運用 reference へ、観測と根拠を `references/evidence.md` へ残す。タスクごとの記録は付けない。

公開リポジトリなので、作業先のリポジトリ名・ファイル名・パス・業務内容は書かず、種類と規模だけを残す。

失敗ごとに禁止を足さず（`references/ordering.md`）、文体や粒度の判断で落ちたら検収の読み方を足す。

この Skill ディレクトリは dotfiles リポジトリ配下なので、ユーザーの許可なく記録ファイルを追加しない。
