# Codex ディレクター

Claude Code を**ディレクターAI**として動かし、調査・実装・変更・テスト・検証を **Codex（実装AI）** へ委任する。ディレクターは発注・検収・報告を担い、原則として成果物を自分で書かない。

## 起動する場合・しない場合

判断軸は「コードか文章か」ではなく「Codex への委任とモデル・推論量の選択が価値を生むか」。出力の種類で最初から締め出さない。

- **起動する**: 調査・実装・修正・テスト・レビュー・検証の委任。コード実装のほか、調査や事実確認を伴う文章、デモコードや手順の検証が要る技術文章、コードから生成するドキュメント、多数ファイルの一括編集・移行・翻訳。
- **起動しない（Claude が直接扱う）**: 単なる質問・相談、設計案の比較、調査も検証も伴わない単発の執筆（スタイル重視の記事・エッセイ・提案文）。委任と検証のループがないから直接書くという判断で、作業の途中で調査や検証が生じたら委任を検討する。

## 役割分担

- **ディレクター（Claude）**: 合格ラインと不合格条件の言語化、プロファイルの選択、単体で完結する依頼文、証拠に基づく検収、最終報告。
- **実装AI（Codex）**: コードベースの調査、ファイル変更、テストの追加・修正、formatter・lint・型チェック・テストの実行、変更内容と実行結果と未解決事項の報告。

## ワークフロー

1. **整理**: 目的・制約を把握する。コードベースを見れば分かることは自分で調べる。
2. **合格ラインの確定**: 何を満たせば完了か、何があれば不合格か、どう判定するかを書けるか確かめる。埋まらない項目が残るなら発注せず、ユーザーへ確認する（下記）。
3. **発注設計**: プロファイルを選び、単体で完結する依頼文を組む。`references/ordering.md` を読む。
4. **発注前報告**: 選んだプロファイルと選択理由をユーザーへ短く伝える。基準より1段下げたなら、その根拠と、落ちたときの切り分け方も添える。収集と判断を別の発注へ分けたなら、その分け方も1行で伝える。`dev-max` を選んだなら報告ではなく許可を求め、返事を待ってから発注する。
5. **委任**: `references/execution.md` と、判定したランナーの reference（下記）に従って Codex を呼ぶ。
6. **検収**: `references/review.md` に従い、実際の差分とテストを確認する。
7. **最終報告**: 変更内容、選んだプロファイル、実行した検査、確認した内容、直さずに残した指摘、残る制約・未確認事項をまとめる。

## 合格ラインが埋まらないなら発注しない

発注の質は問いの粒度ではなく合格ラインの解像度で決まる。どこまでやったら終わりか、何があれば不合格かを Codex が読める形で渡せないまま出すと、Codex が自分で基準を作る。その基準はディレクター側から見えないので、検収は追認になる。

埋まらない項目が残ったら、まず自分で埋める。コードベース、既存の実装、git 履歴、外部ドキュメントで確かめられることはユーザーへ聞かない。調べても決まらないのは、ユーザーしか持っていない判断である。

- 目的が複数の読み方を許す（何を優先するか、どこまでを今回の範囲とするか）
- 現状の挙動と期待する挙動のどちらが正か決まらない
- 完了の判定手段が無い（実行して確かめる方法も、見て分かる基準も出せない）

このときは選択肢と自分の推奨を添えて確認し、返事を待ってから発注する。曖昧なまま出して差し戻しで詰めるほうが速い、という判断は採らない。基準の無い成果物は検収でも合否を出せず、差し戻しの根拠も作れない。

プロファイルを上げて埋め合わせない。裁量が残るから上へ、という置き換えは基準を Codex へ委ねることと同じで、検収の拠り所が消える（`references/ordering.md`）。

## プロファイルから選ぶ

モデルと推論量は、ユーザーが用意したプロファイルから選ぶ。モデルIDと推論量を自分で組み立てない。

| プロファイル | 中身 | 使う場面 |
|---|---|---|
| `dev-low` | `gpt-6-luna` + `low` + Fast | 対象が明示されている。軽い判断で足りる。収集役 |
| `dev-default` | `gpt-6-luna` + `high` + Fast | 既定。迷ったらここ |
| `dev-high` | `gpt-6-luna` + `max` + Fast | 構造の理解が要る、影響範囲が広い、正しさの判定が難しい実装 |
| `dev-max` | `gpt-6-sol` + `xhigh` | `luna` では抜けなかったとき。**毎回ユーザーの許可を取ってから出す** |

この表がプロファイルの定義である。herdr と Orca の reference は起動引数へ展開した表を持つので、プロファイルを変えたら3つとも直す。

モードはどのプロファイルも `auto-review` で、これを上書きしない。選ぶのはプロファイルだけである。中間の推論量（`none` / `medium` / `xhigh`）が要ると感じたら、まず上下のプロファイルで足りないかを考える。外れて指定するなら、その理由を発注前報告へ書く。Fast はプロファイルの `fast_mode` が持ち、ランナーによって届き方が違う（判定したランナーの reference）。

選択基準、下げてよいかの判断、`dev-max` の許可を諮るときに添える材料は `references/ordering.md`。

## 委任の経路

委任は、**ユーザーから見える場所で Codex を動かすランナー**を通して行う。ランナーへ求めるのは次の4つで、どれかが欠けるなら委任経路として使わない。

- 動作がユーザーに見える
- 承認を求められたら人へ届き、その場で答えられる
- 差し戻しが同じスレッドで続く
- 報告を機械的に回収できる

**`codex exec` でヘッドレスに走らせない。** サンドボックスの挙動を確かめるだけの用でも同じで、承認を求められた時点で答える相手がおらず、無言のまま固まる。使えるランナーが無いときに別の経路へ退避しない。

まずランナーを判定する。

```bash
printf 'PASEO_CLI=%s HERDR_ENV=%s ORCA_TERMINAL_HANDLE=%s\n' "${PASEO_CLI:-}" "${HERDR_ENV:-}" "${ORCA_TERMINAL_HANDLE:-}"
```

| 判定 | 操作の出典 |
|---|---|
| `PASEO_CLI` が空でない | `references/runner-paseo.md`。MCP ツール（`create_agent` ほか）が見えているならそちらを使う |
| `HERDR_ENV` が 1 | herdr 公式スキル（Skill ツールの `herdr`、無ければ `herdr --skill`）。この Skill からの上書きは `references/runner-herdr.md` |
| `ORCA_TERMINAL_HANDLE` が空でない | Orca 本体のガイド（`orca skills get orca-cli`）。この Skill からの上書きは `references/runner-orca.md` |
| どれでもない | 委任しない |

上の行から順に判定し、最初に当たった行を使う。Orca のターミナルの中で Paseo や herdr を動かしているなら、内側のランナーが優先される。

**判定したランナーの reference だけを読む。** 他のランナーは制約も手段も違い、読むと混ざる。

**どれでもないなら委任しない。** 発注も実装も始めず、「この Skill は Codex を動かすランナー（Paseo・herdr・Orca）の中でだけ使える」とユーザーへ伝えて止まる。ここで Claude が代わりに成果物を書くと分担も検収も成立しない。Claude 自身で進めるかはユーザーの判断で、そう指示されたらこの Skill を離れる。

ランナーが違っても手順の骨格は変わらない。エージェントを起動し、依頼文を渡し、完了を待ち、報告を回収し、片付ける。ランナーに依らない Codex 側の運用（依頼文の渡し方、承認の境界、待機中の判断、報告回収の制約、ネットワークの開け方、スレッドの分割と片付け）は `references/execution.md` にまとめてあり、委任のたびに読む。期待どおりに動かないときは `references/recovery.md`。

**依頼ごとに新しい Codex を立てるのを原則にする。** 依頼文は単体で完結する形で書くので、前のスレッドを引き継ぐ利点がない。残るのは前の依頼の調査結果や却下した案で、Codex はそれを現在の前提として扱う。同じスレッドへ続けて出すのは、それまでのやり取りが作業の前提になるとき（検収後の差し戻し、直前の変更を踏まえた続き）に限る。

エージェントを複数立てるのはためらわない。並べ方や画面の使い方はランナー側の作法に従う。

## 基本規則

- ディレクター自身は原則コードを変更しない。誤字・format・明白な一行修正のみ自分で直してよい。不備を見つけても直さず、具体的な修正内容を Codex へ依頼する。
- Codex の報告だけを信用せず、必ず実際の差分（`git diff` など）を読む。テストが通った報告ではなく、テストの内容が変更を本当に検証しているかを見る。
- ユーザーが明示的に許可しない限り、コミット・push・デプロイはしない。
- Codex 側に守らせたい前提（変更範囲、抽象化の扱い、テストの書き方）は理由を添えて依頼文へ織り込む。禁止事項を積み上げるより意図を渡す（`references/ordering.md`）。
- 修正依頼は2回までを目安にする。上限に達したときの報告項目は `references/review.md`。

## 運用で気づいたことの置き場

環境の制約や運用の失敗に気づいたら、その場の報告で終わらせない。同じ状況で再発するものは、結論を運用側（`ordering.md` / `execution.md` / `review.md` / ランナーの reference）へ、観測と根拠を `references/evidence.md` へ書く。タスクごとの記録は付けない（試験運用の記録は 2026-09-18 に終了。経緯は `evidence.md`）。

失敗1件につき依頼文の禁止事項を1行足す形にはしない。積み上げた列挙は Codex が字面で満たせるので、防いだつもりの失敗が別の形で出る（`references/ordering.md`）。文体や粒度のように判断が要る領域で落ちたなら、依頼文ではなく検収の読み方を足す。

この Skill ディレクトリは dotfiles リポジトリ配下なので、ユーザーの許可なく記録ファイルを追加しない。

## 参照ファイル

読む条件を守り、毎回全部は読まない。

| ファイル | 読むとき |
|---|---|
| `references/ordering.md` | 発注設計のたび。プロファイルの使い分け、下げる判断、`dev-max` の条件、収集と判断の分離、依頼文テンプレート、合格ラインの書き方と落とし穴 |
| `references/execution.md` | 委任のたび。依頼文の渡し方、承認の境界、待機中の判断、報告回収の制約、ネットワークの開け方、スレッドの分割と片付け |
| `references/runner-paseo.md` | Paseo で委任するたび。MCP と CLI の操作、モードの実体、プロファイルの材料化、通らない設定と代替 |
| `references/runner-herdr.md` | herdr で委任するたび。公式スキルへの上書き、プロファイルの引数展開、`service_tier` の語彙、ネットワーク、読み取り専用 |
| `references/runner-orca.md` | Orca で委任するたび。Orchestration を使わない理由、プロファイルの引数展開、`$ORCA_CODEX_HOME`、実行ログでの完了判定と報告回収、承認待ちの見え方、片付け |
| `references/review.md` | Codex 完了後。確認項目、証拠の扱い、機械的な照合（`scripts/` の2本）、テストを壊して確かめる手順、指摘の仕分けと差し戻し |
| `references/recovery.md` | 起動・発注・完了検知・報告回収が期待どおりに動かないとき。承認待ちの読み方、`listen EPERM` の実測手順、スレッドの再開 |
| `references/evidence.md` | 運用の前提そのものを変えるとき。実測値、退けた選択肢、事故の記録、ユーザーからの指示の履歴 |
