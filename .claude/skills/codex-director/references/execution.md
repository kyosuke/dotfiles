# Codex を動かす

`../SKILL.md` の骨格から外れる操作が要るときに読む。起動フラグ、承認の境界、並列の可否、報告回収の制約、ネットワーク、スレッドの分割と片付けを置く。ランナーごとのコマンドは `runners.md`、詰まったときの復旧は `recovery.md`、実測の詳細は `evidence.md`。

ここに書くのは Codex 側の話で、ランナーには依らない。ランナーの操作（起動、発注、状態の読み方、報告の取り方）はそちらの出典に従い、想像で補わない。

## 起動時に決めること

- **段を明示する。** モデルと推論量は毎回渡し、`~/.codex/config.toml` の既定に落とさない（`ordering.md`）。
- ファイル変更にフラグは要らない。ユーザーの設定（`workspace-write`）で既定で書ける。調査だけを頼むなら読み取り専用で起動する（`-s read-only` 相当）。
- ネットワークやループバックを要する検証が発注に含まれるなら、依頼文で昇格の要求を許す（下記）。
- 承認方針は既定の `on-request` のまま起動する。`-a untrusted` は `codex --help` にある正式な値だが、trusted 集合（`ls`・`cat`・`sed` など）の外にあるコマンドをすべて承認へ上げる（`find` も対象になった）。ディレクターは承認できないので、そのセッションでは作業が進まない。
- モデル名・推論量・オプションがこのファイルの記述と食い違ったら、想像で補わず `codex --help`・`~/.codex/models_cache.json`・ランナーのヘルプで実際を確認する。

## 発注する

依頼文は Write ツールでファイルへ書いてから渡す。ヒアドキュメントは使わない。理由は2つ。文中のバックティックがコマンド置換として実行される（実運用で `` `wrangler dev` `` が起動してサーバーとして残り、仕様の核が欠落した依頼文が渡った）。加えて、サンドボックスや権限に触れる文言を含むヒアドキュメントは Claude Code のclassifierに止められることがある。

完了の判定はランナーが返す状態で行い、自分でポーリングしない。承認待ちで止まったら「承認を求められたとき」へ。

所要時間は、読み取りだけの小さな依頼で12〜40秒。実装を伴う依頼は20分を超えることがある。Bash ツールの上限は10分なので、長い依頼は `run_in_background: true` で投げ、完了通知を受けてから読む。

## 待機中の判断

- **ファイルが未変更でも失敗と判断しない。** Codex は数分から十数分を調査に使ってから書き始める（実運用では開始3分後はまだ調査中だった）。
- 完了通知を受け取る前に、検収と最終報告を終えない。
- 待機中は同じ作業ツリーを触らない。**書き込みを伴う委任を同一作業ツリーで並列実行しない。** 画面やエージェントを分けても作業ツリーは共有されるので、表示の分離は並列化の根拠にならない。書かせる並列化には別の worktree / workspace を使い、作業ディレクトリをそちらへ向ける。
- 読み取りだけの委任（読み取り専用で起動した調査・レビュー）は同じ作業ツリーで並走してよい。互いの結果を突き合わせたい調査は、むしろ分けて同時に走らせる。読み取り専用で起動できないランナーでは、この前提が崩れる（`runners.md`）。

## 消費を確かめる

`dev-max` の許可を諮るときや、下げた段の効果を測るときに使う（`ordering.md`）。取り方はランナーで違う（`runners.md`）。TUI が使えるなら `/status` が適用中のモデル・推論量・週次の残量を返す（`Model: gpt-5.6-luna (reasoning none, summaries auto)` / `Weekly limit: 93% left (resets 16:53 on 18 Aug)`）。ローカルのUIコマンドなのでターンを消費しない。

**画面のフッター表示を段の確認に使わない。** `model_reasoning_effort=none` で起動したセッションが、フッターには `gpt-5.6-luna default fast` と出しながら `/status` では `reasoning none` を返した。起動直後のバナーは `/status` と一致する。

## 報告を回収する

回収できたのは実測で200行台なので、これを超える報告は分割して依頼する。

**終端マーカーを依頼文に入れない。** 完了の検知はランナーの仕事で、待機コマンドが状態として返すので判定が二重になる。取りこぼしの検出にも使えない。画面から読むランナーでは下端が基準なので、失われるのは先頭である。機械的に判定したいならマーカーは報告の**先頭**へ置く。

**画面の記録は証拠ではない。** 見えているのは Codex が描いた画面であり、コマンドの生出力ではない。Codex はツール出力を `… +464 lines` のように畳むので、畳まれた部分は読めない。報告と画面が食い違ったら、どちらも信じずに、出力が短くなる形で追試させる（実害の記録は `evidence.md`）。実行ログの中身も Codex の内部状態であって成果物ではない。検収は画面でもログでもなく `git diff` で行う（`review.md`）。

## 承認を求められたとき

止まったら、ランナーから何を聞かれているかを読む。

**ディレクターは承認を代行しない。** Claude Code のclassifierが承認の代理入力を止める。実際に止められたのは、承認プロンプトへキー入力で承認を送る操作と、権限昇格の文言を含むヒアドキュメントである。Codex へ「ネットワークが要るコマンドは昇格を要求してよい」と依頼文で許すのは、承認の代行ではないので止まらない（2026-09-18 実測。以前ここには止まると書いていたが、誤りだった）。

却下は通る。実測では却下したファイルは作られなかった。したがって承認が必要な場面は、見えている画面でユーザーが答える。ディレクターは何を求められているかをユーザーへ伝えて待つ。

却下した直後は Codex が「どうするか指示して」で待つため、状態は承認待ちのままに見える。通常の発注を送ると進む。

**すべての承認が人まで来るとは限らない。** `~/.codex/config.toml` の `approvals_reviewer = "auto_review"` が効いていると、`on-request` の承認のうち対象になるものは auto-reviewer のサブエージェントが処理する（Paseo の既定モード `auto-review` も同じ設定を当てる）。実測したセッションの `turn_context` は `approval_policy: on-request` と `approvals_reviewer: auto_review` を同時に持っていた（2026-09-12）。止まらずに進んだことを、承認が不要だった証拠として読まない。何が自動で通ったかは差分で確かめる（`review.md`）。

## スレッドを分ける判断と片付け

新しい依頼は新しいエージェントで出す（`../SKILL.md`）。同じスレッドへ続けるのは、それまでのやり取りが作業の前提になる場合に限る。

- 検収で見つけた不備の差し戻し
- 直前の変更を踏まえた追加作業で、その調査を引き継ぐほうが速いもの
- 依頼文へ書き写すには大きすぎる文脈（長い調査の結果など）を土台にする作業

迷ったら分ける。判定はその文脈を依頼文へ数行で書けるかで足りる。書けるなら新しいスレッドへ渡す。

差し戻しは同じエージェントへ発注を送るだけで同じスレッドが続く。明示的に再開する操作は要らない。送る前に、そのエージェントが待機状態（承認待ちではない）であることを確認する。承認待ちのまま送ると、返ってきた承認要求が新しいものか直前のものかを区別できない。

終わったら自分が作ったエージェントだけ畳む。放置すると、同一作業ツリーで別の Codex が走る事故が起きる。Codex のセッションID（`/quit` 時に表示される `codex resume <UUID>` と一致する）は、あとで文脈が要ると分かったときの再開に使えるので、長い作業では控えておく（手順は `recovery.md`）。

## ネットワークとローカルバインド

Codex の workspace-write サンドボックスは既定でネットワークを閉じる。macOS の Seatbelt が `127.0.0.1` への bind まで拒否するため、`@cloudflare/vitest-pool-workers` の workers プール（workerd がループバックを listen する）と `wrangler dev` が動かない。失敗の見え方が厄介で、vitest は起動できたプールの件数だけを passed として表示するので、workers プールが落ちても「Tests 36 passed」と出る。Codex はこれを成功として報告した。

**開けるのはコマンド単位の昇格である。** 依頼文で `sandbox_permissions: require_escalated` の要求を許すと、Codex は justification を添えて要求し、auto-reviewer が可否を決める。通ったコマンドだけがサンドボックス外で走り、セッション全体の権限は変わらない。ランナー側でサンドボックスを開ける設定（Paseo の `--mode full-access`、Codex のネイティブ引数）は使わない（`runners.md`）。

**`~/.codex/config.toml` へは書かない。** グローバルなので全 Codex 実行（TUI 含む、クライアント案件のリポジトリ含む）で外向きが開き、戻し忘れがそのまま恒久設定になる。

運用は次のとおり。

- ネットワークやループバックを要する検証（workers プール、`wrangler dev`、外部APIを叩く取得、`wrangler --remote`）が発注に含まれるなら、依頼文で昇格を許す。ユーザーの方針で、これは都度の確認を要しない（2026-08-09、2026-09-18）。許さないまま出すと、Codex は一度も実行できないテストを論理だけで書くことになり、差し戻しが増える。
- 要らない発注では許さない。実装とサンドボックス内で完結する検査までを委任する形を崩さない。
- 昇格の可否は auto-reviewer が決める。ディレクターは代行しないし、人へ上げ直す設定変更も提案しない（2026-09-18、ユーザーからの指示）。
- 何回・どのコマンドで昇格したかは報告に書かせ、検収で確かめ、trial-log にも残す（`review.md`）。
- 昇格を許さなかった発注では、`<verification>` にサンドボックスで完走するコマンドだけを書き、フルスイートはディレクター側で実行すると明記する（`ordering.md`）。いずれの場合も、テストを追加させたら件数はディレクター側で数える（`review.md`）。Codex 側の実行は二重確認の片方でしかない。

昇格している間の代償は、そのコマンドが全ディスクの読み取りと外向き通信を持つことにある。1Password でマウント中の `.env` も読め、リポジトリ内容や取得ページ経由の prompt injection による持ち出し経路が増える。通信先は制限されない。セッション全体が開きっぱなしにならないぶん、露出はサンドボックスを開ける運用より小さい。
