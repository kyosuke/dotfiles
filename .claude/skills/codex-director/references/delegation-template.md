# 発注前の整理と依頼文テンプレート

依頼文を書く前に読む。

## 発注前に整理する8項目

Codex を呼ぶ前に次を明確にする。情報が足りなくても、コードベースを見れば判断できることは先に自分で調べる。ユーザーへの質問は重大な仕様判断だけに絞る。

1. 目的
2. 現在の問題
3. 対象範囲
4. 実装上の制約
5. 変更してはいけないもの
6. 完了条件
7. 実行する検査コマンド（formatter・lint・型チェック・テスト）
8. Codex に報告させる内容

## 依頼文テンプレート

依頼文は、このClaudeとの会話を知らなくても単体で理解できる形にする。Codex にもコードベースを探索させられるので、不要なファイル全文を貼らない。必要十分な長さにする。

```text
<task>
作業の目的と、実施する変更
</task>

<context>
現在の問題、確認済みの事実、関連するファイル
</context>

<constraints>
変更範囲、禁止事項、守るべき既存仕様
</constraints>

<acceptance_criteria>
完了と判断できる具体的な条件
</acceptance_criteria>

<verification>
実行するテスト、型チェック、lint など
</verification>

<report>
変更ファイル、実行結果、判断に迷った点、未解決事項
</report>
```

## 依頼文に必ず含める指示

Codex がこの Skill の基本規則に沿って動くよう、依頼文（主に `<constraints>`）へ次を織り込む。

- 変更範囲を目的より広げない。
- 適切な抽象が明確でない限り、早まった共通化をしない。
- テストは実装詳細でなく期待する振る舞いを検証する。修正前の壊れた実装でも通るテストにしない。
- テストが書きにくいときは無理に複雑化せず、設計上の問題として報告する。
- コミット・push・デプロイはしない。
- 既存の設計・技術スタックを尊重し、不要な依存や抽象化を足さない。
- 調査のみで編集させたくないときは「ファイルを変更せず調査のみ」と明記する（実装タスクは既定で書き込み可のため）。

`<verification>` には、その環境で実際に使う検査コマンドを具体的に書く（例: 型チェック・lint・テストの各コマンド）。何を実行し、何が通れば完了かを Codex 側だけで判定できるようにする。
