# 発注前の整理と依頼文テンプレート

依頼文を書く前に読む。

## 発注前に整理する8項目

Codex を呼ぶ前に次を明確にする。情報が足りなくても、コードベースを見れば判断できることは先に自分で調べる。ユーザーへの質問は重大な仕様判断だけに絞る。

1. 目的
2. 現在の問題
3. 対象範囲
4. 実装上の制約
5. 変更してはいけないもの
6. 完了条件
7. 実行する検査コマンド（formatter・lint・型チェック・テスト）
8. Codex に報告させる内容

## 依頼文テンプレート

依頼文は、このClaudeとの会話を知らなくても単体で理解できる形にする。Codex にもコードベースを探索させられるので、不要なファイル全文を貼らない。必要十分な長さにする。

```text
<task>
作業の目的と、実施する変更
</task>

<context>
現在の問題、確認済みの事実、関連するファイル
</context>

<constraints>
変更範囲、禁止事項、守るべき既存仕様
</constraints>

<acceptance_criteria>
完了と判断できる具体的な条件
</acceptance_criteria>

<verification>
実行するテスト、型チェック、lint など
</verification>

<report>
変更ファイル、実行結果、判断に迷った点、未解決事項
</report>
```

## 依頼文に必ず含める指示

Codex がこの Skill の基本規則に沿って動くよう、依頼文（主に `<constraints>`）へ次を織り込む。

- 変更範囲を目的より広げない。
- 適切な抽象が明確でない限り、早まった共通化をしない。
- テストは実装詳細でなく期待する振る舞いを検証する。修正前の壊れた実装でも通るテストにしない。
- テストが書きにくいときは無理に複雑化せず、設計上の問題として報告する。
- コミット・push・デプロイはしない。
- 既存の設計・技術スタックを尊重し、不要な依存や抽象化を足さない。
- 調査のみで編集させたくないときは「ファイルを変更せず調査のみ」と明記する（実装タスクは既定で書き込み可のため）。

## 完了条件を狭めすぎない

`<acceptance_criteria>` は、目的を満たす実装が複数ありうるなら許容範囲まで書く。実運用では、判定条件を1つの数値に絞った依頼文のせいで、正しく動く実装を差し戻す無駄が発生した。検証したい振る舞いを書き、実装の選び方まで決めつけない。

## 検証できない実装詳細を受入条件に書かない

サンドボックスの外でしか確かめられない詳細を `<acceptance_criteria>` に書くと、Codex は確認できないまま従い、実行段階で落ちる。差し戻しの往復がそのまま増える。

実運用では、本番 D1 からローカル D1 へデータを移す実装で2回続けて起きた。「除外するのは `sqlite_%` と `d1_migrations`」と書いたら内部テーブル `_cf_KV` を拾って rowid 不在で落ち、「`BEGIN` / `COMMIT` を維持する」と書いたらローカル D1 が SQL のトランザクション文を拒否して落ちた。どちらもネットワークが要るため Codex 側では検証できない。

判断の順は次のとおり。

1. その詳細をディレクター側で確かめられるなら、先に実行して確認し、結果を `<context>` に貼る。
2. 確かめられないなら書かない。目的と満たすべき振る舞いだけを渡し、実装の詳細は Codex に決めさせる。
3. どうしても方針を指定するなら「未検証の想定」と明示し、違っていたら報告するよう頼む。

## 検査コマンドの書き方

`<verification>` には、その環境で実際に使う検査コマンドを具体的に書く（例: 型チェック・lint・テストの各コマンド）。何を実行し、何が通れば完了かを Codex 側だけで判定できるようにする。書く前に次を確認する。

- サンドボックスで完走するコマンドか。Codex は `127.0.0.1` を listen できないため、workers プールを使うテストや `wrangler dev` は起動しない（理由と検証は `sandbox-network.md`）。該当する場合は走る範囲だけを指定し（例: `npx vitest run --project node`）、フルスイートはディレクター側で実行すると依頼文に書く。
- check と write のどちらか。`npm run format` が check モードの環境で、Codex が自力で `format:write` へ切り替えた例がある。意図するコマンドを正確に指定する。
- テストを追加・変更させるなら期待件数を書く。「既存 N 件 + 新規 M 件で合計 X 件」と示し、報告にも件数を含めさせる。プールの起動失敗でテストが走らないまま成功に見える事故を、この1行で検出できる。
