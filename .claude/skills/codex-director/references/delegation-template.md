# 発注前の整理と依頼文テンプレート

依頼文を書く前に読む。

## 発注前に整理する8項目

Codex を呼ぶ前に次を明確にする。コードベースを見れば判断できることは先に自分で調べ、ユーザーへの質問は重大な仕様判断だけに絞る。

1. 目的
2. 現在の問題
3. 対象範囲
4. 実装上の制約
5. 変更してはいけないもの
6. 完了条件
7. 実行する検査コマンド（formatter・lint・型チェック・テスト）
8. Codex に報告させる内容

## 依頼文テンプレート

依頼文は、このClaudeとの会話を知らなくても単体で理解できる形にする。Codex もコードベースを探索できるので、不要なファイル全文は貼らない。

```text
<task>
作業の目的と、実施する変更
</task>

<context>
現在の問題、確認済みの事実、関連するファイル
</context>

<constraints>
変更範囲、越えてはいけない境界とその理由、守るべき既存仕様
</constraints>

<acceptance_criteria>
完了と判断できる具体的な条件
</acceptance_criteria>

<verification>
実行するテスト、型チェック、lint など
</verification>

<report>
変更ファイル、実行結果、判断に迷った点、未解決事項
</report>
```

## 依頼文は意図で書き、禁止の列挙で埋めない

差し戻しのたびに禁止事項を1行足していくと、依頼文は長くなるのに成果物は良くならない。Codex は書かれた字面を満たしながら要点を外し、列挙の外側にある細部が崩れる。

公式の推奨も同じ方向を向く。Anthropic は、してはいけないことではなくしてほしいことを書き、指示の背景や動機を添えると意図が伝わるとしている。手順を細かく規定するより一般的な指示のほうが良い結果になるとも書いている（[Prompting best practices](https://platform.claude.com/docs/en/docs/build-with-claude/prompt-engineering/claude-prompting-best-practices)、2026-08参照）。OpenAI は GPT-5 について、指示を精密に守るがゆえに矛盾した指示や曖昧な指示の害が他のモデルより大きく、モデルが矛盾の調停へ推論を費やすと説明している（[GPT-5 prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide)、2026-08参照）。禁止事項を積み上げた依頼文は、この矛盾を作りやすい。

書き方の順は次のとおり。

1. 何のための作業かを書く。制約には、それが要る理由を1文添える。理由があれば、列挙しなかった場面でも Codex が判断できる。
2. 期待する形は手本で示す。既存のファイル・関数・記事を指し、その粒度に合わせるよう書く。同じ内容を規則へ翻訳し直さない。
3. 判断が要る領域は判断させる。満たすべき振る舞いを渡し、達成の手段は選ばせる（下の「完了条件は振る舞いで書き、脆い手段だけを塞ぐ」）。
4. 明示的に塞ぐのは、外れると害が出るものだけにする。

範囲と対象を曖昧にする話ではない。どのファイルか、何を満たせば完了か、どの検査を通すかは具体的に書く。決めないのは達成の手段と出力の形であって、作業の輪郭ではない。

## 報告前の裏取りを依頼文で要求する

Codex は求められなければ、自分の作業を成功した前提で要約する。次をそのまま `<report>` の直前に置く。実運用では、入れて以降は報告の全項目が行番号つきになり、移し漏れの照合が1件ずつ根拠つきで返ってきた。

```text
<self_check>
報告を書く前に、次を実行する。省略しない。

1. 報告に書こうとしている主張を、実際のコードで確認する。ファイル名と行番号を添える
2. `git diff` を最初から最後まで通しで読む。依頼していない変更が混ざっていないか確認する
3. この依頼文が「保存すべき挙動」として挙げた項目を1つずつ照合し、各項目が満たされている根拠を示す
4. 追加・変更したテストが、変更前の実装でも通ってしまわないか確かめる。通るなら、そのテストは変更を検証していない
5. 確認できていないことを「確認済み」と書かない。未確認は未確認と明示する
</self_check>
```

この節は検収を置き換えない。実装AIが自分では検証しきれない領域（テスト網羅の不足、サンドボックスで走らない検査、完了誤認）は残るので、ディレクター側の検収は同じだけ行う。

## 依頼文へ織り込む前提

この Skill が置いている前提は Codex 側から見えないので、依頼文（主に `<constraints>`）へ理由ごと渡す。

- 変更範囲を目的より広げない。検収では差分を通しで読むため、目的外の変更が混ざると全体が不合格になる。
- 適切な抽象が見えるまで重複を許容してよい。早まった共通化は誤った依存を残すので、重複のほうがましである。
- テストは期待する振る舞いを検証する。修正前の実装でも通るテストは、変更を検証していない。
- テストが書きにくいときは、無理に複雑化せず設計上の問題として報告してよい。ねじれた実装より、その報告のほうが役に立つ。
- 既存の設計・技術スタックを尊重する。この依頼の目的は、そこへ手を入れることではない。

理由を添えずに境界として書くのは次の2つである。外れた時点で害が出るので、判断の余地を残さない。

- コミット・push・デプロイはしない。
- 調査だけを頼むなら「ファイルを変更せず調査のみ」と明記する。実装タスクは既定で書き込み可のため、書かなければ編集される。

## 完了条件は振る舞いで書き、脆い手段だけを塞ぐ

`<acceptance_criteria>` は、目的を満たす実装が複数ありうるなら許容範囲まで書く。実運用では、判定条件を1つの数値に絞った依頼文が、正しく動く実装を差し戻させた。検証したい振る舞いを書き、実装の選び方まで決めつけない。

例外は、条件を満たす手段の一部が上流の変更に対して脆いときである。エラーメッセージ、識別子、生成物の出力形状のように満たし方が複数ある領域では、Codex は最短の手段を選び、それが脆いほうでも受入条件は全部満たす。ここで「Xに依存するな」と禁止だけを書いても、依存先が別の壊れやすい対象へ移るだけで終わる。根拠にしてよい対象を列挙し、想定される代替の失敗を1つ潰しておく。「authored な設定ファイル、生成物の JSON、export 文の走査だけを根拠にしてよい」「エラーメッセージの文言を作ってよいのは、それを throw する関数だけ」と書けば、手書きのパーサや文字列置換の余地は消える。列挙できないなら、その検査が成立するかを先に疑う。

実運用の2件。生成バンドルを読む検査で「バンドラ生成の識別子に依存しない形にする」と差し戻したら、依存先が `default: () => ident` という出力形状へ移り、ブレースを数える手書きのパーサ100行が入った（検査を取り下げ、依存バージョンの固定へ振り替えた）。エラーメッセージが呼び出し側の引数名を指すことだけを条件にしたら、上流の Error を `replace(/\bfrom\b/g, "startDate").replace(/\bto\b/g, "endDate")` で書き換える実装が来た（"to" は英文に普遍的に現れるので、上流の文言が増えるだけで別の箇所が壊れる）。どちらも条件の照合だけでは合格になる。

## `<self_check>` のgrepは対象の場所まで絞って書く

`<self_check>` にgrepを書くときは、範囲を指定した時点でその範囲から消す指示になると理解する。消す対象をファイル単位で特定できるなら、grepの範囲もそのファイルへ絞る。絞れないなら、grepではなく「この関数のこの分岐から外す」と場所で指定する。

実運用では、`grep -rn "対象Project外" src scripts tests` を検収条件にしたところ、消したかった箇所とは別に、本番の別経路の表示名として使われていた文字列まで消えた。条件の照合だけでは指示どおりに見えるため、`git diff` を通しで読んで発見した。team-activity-observerの週次DM本文フォーマット調整で、2026-08-06に4回発注したうちの1回で発生した。

## 型定義だけで実データの形を前提にしない

型定義は「そう扱う」という宣言であって、保存済みデータがその形であることを保証しない。依頼文の `<context>` に型を貼る前に、実データを1件取り出してキーを列挙する。

とくに型と実データがずれるのは次の場合である。

- スキーマが後から厳しくなり、古い行が旧形状のまま残っている
- パース層がデフォルト値を補っており、型が補完後の形を表している
- 外部APIのレスポンスをそのまま保存している

実運用では、`projects: Array<...>` が必須の型定義を根拠に依頼したところ、DBの実データにはプロパティ自体がなく、新規スクリプトが `Cannot read properties of undefined` で落ちた。本番コードはvalibotのパースで `?? []` を通るため無傷だった。team-activity-observerの週次DM本文フォーマット調整で、2026-08-06に4回発注したうちの1回で発生した。

## 検証できない実装詳細を受入条件に書かない

サンドボックスの外でしか確かめられない詳細を `<acceptance_criteria>` に書くと、Codex は確認できないまま従い、実行段階で落ちる。差し戻しの往復がそのまま増える。

実運用では、本番 D1 からローカル D1 へデータを移す実装で2回続けて起きた。除外対象を `sqlite_%` と `d1_migrations` に限ると指定したら内部テーブル `_cf_KV` を拾って rowid 不在で落ち、`BEGIN` / `COMMIT` の維持を指定したらローカル D1 がトランザクション文を拒否して落ちた。どちらもネットワークが要るため Codex 側では検証できない。

判断の順は次のとおり。

1. その詳細をディレクター側で確かめられるなら、先に実行して確認し、結果を `<context>` に貼る。
2. 確かめられないなら書かない。目的と満たすべき振る舞いだけを渡し、実装の詳細は Codex に決めさせる。
3. どうしても方針を指定するなら「未検証の想定」と明示し、違っていたら報告するよう頼む。

## 検査コマンドの書き方

`<verification>` には、その環境で実際に使う検査コマンドを具体的に書く（型チェック・lint・テストの各コマンド）。何を実行し、何が通れば完了かを Codex 側だけで判定できるようにする。書く前に次を確認する。

- サンドボックスで完走するコマンドか。Codex は既定で `127.0.0.1` を listen できないため、workers プールを使うテストや `wrangler dev` は起動しない。該当するなら、ペインの起動時にネットワークを開けて全部走らせる（`sandbox-network.md`）。開けずに出すなら走る範囲だけを指定し（例: `npx vitest run --project node`）、フルスイートはディレクター側で実行すると依頼文に書く。
- check と write のどちらか。`npm run format` が check モードの環境で、Codex が自力で `format:write` へ切り替えた例がある。意図するコマンドを正確に指定する。
- テストを追加・変更させるなら期待件数を書く。「既存 N 件 + 新規 M 件で合計 X 件」と示し、報告にも件数を含めさせる。プールの起動失敗でテストが走らないまま成功に見える事故を、この1行で検出できる。

## 文章成果物では手本を示し、構成を決め切らない

分量には下限を書かず、短くなった結果を減点しないと明記する。そのうえで「節末に前段の要約段落を置かない。意味づけの一文だけを置く」は書く価値がある。2026-08-06にknowledgeリポジトリでlunaへ発注した記事2本で、節末に前段の言い直しが積まれた（3節中2節と4節中3節、どちらもhigh、差し戻し1回で解消）。下限を書かなかった2本目でも出たので、下限を外すだけでは足りない。

構成は手本で示す。既存の記事を指し、節の粒度と解釈メモの書き方をそこから読ませる。節の見出しの文字列、節内の構成要素、項目数までを列挙する形は採らない。

効果がないからではない。2026-08-11に同じリポジトリで4件連続して発注し、見出しを列挙して「これ以外の節を作らない」と書いた回は、節を増やす癖と同じ主張の重複が実際に止まった。代わりに枠と枠の継ぎ目が崩れた。地の文の句点の脱落、出典3要素を1文へ詰め込む、コードブロック直後に導入なしで始まる箇条書き、「対処は〜させる」の主述のねじれ。指定した項目は全部埋まっているのに、つなぎだけが雑になる。枠を増やすほど、字面を満たしながら要点を外す方向へ寄る。

したがって、文体で落ちたときに依頼文の指定を増やす反応をしない。4件はいずれも事実関係と検査を初回で通し、落ちたのは文体だけで、差し戻し1〜2回で合格した。文体は判断の領域なので、検収で読んで差し戻す（`review-checklist.md`）。
