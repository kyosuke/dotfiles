# 検収と差し戻し

Codex 完了後に読む。報告だけを信用せず、必ず実際の差分を自分で読む。

## 検収の確認項目

`git diff`・`git status` などで実際の変更を読み、次を確認する。

- 要求をすべて満たしているか
- 依頼していない変更が混ざっていないか
- 差分が必要以上に大きくないか
- 既存の設計や技術スタックを尊重しているか
- 不要な依存や抽象化を追加していないか
- 正常系だけでなく失敗時も安全か
- テストが修正内容を本当に検証しているか
- 修正前の壊れた実装でも通るテストになっていないか
- 指定した formatter・lint・型チェック・テストが実際に実行されたか
- 未確認事項を、確認済みであるかのように報告していないか

テストは中身まで読む。「テストが通った」という報告だけでは不十分で、そのテストが今回の変更を検証しているか、壊れた実装を素通しする作りになっていないかを見る。

## テストが本当に欠陥を検出するか確かめる

テストを読むだけでは、それが欠陥を捕まえるかは分からない。実装をわざと壊し、意図したテストだけが落ちることを確認する。実運用ではこの工程が、Codex 自身の検証をすり抜けた穴（テストが存在しない領域の欠陥）を見つけた。

手順は次のとおり。対象ファイルを退避し、変更点ごとに1箇所だけ壊してテストを走らせ、毎回退避から戻す。

1. 変更されたファイルをスクラッチ領域へコピーしておく
2. 主要な変更につき1つ、破壊的な書き換えを当てる（境界条件の反転、ガード節の削除、条件式の除去など）
3. テストを実行し、落ちたテストが「その変更を検証しているはずのテスト」1件かを見る
4. ファイルを退避から復元し、次の変更へ進む

落ちない変更があれば、その箇所は検証されていない。落ちるテストが多すぎる場合も、テストが変更を特定できていない兆候として扱う。作業後は必ず全ファイルが元に戻り、テストが通る状態に復帰したことを確認する。

この工程はディレクターAI自身が行ってよい。成果物を書き換えるのではなく、検証のために一時的に壊して戻すだけだからである。

## 非コード成果物の場合

上記の項目はコード成果物を前提にしている。文章・ドキュメントなど非コードの成果物を委任した場合は、精神を適用する。報告でなく成果物そのものを読み、事実・出典・デモコードの動作を裏取りし、記述が確認済みの事実に基づいているかを見る。技術文章ならデモコードを実際に実行して結果が本文と一致するか確認する。

## 不備を見つけたとき

自分で直さず、問題のあるファイル・挙動・テストを具体的に示して、同じ Codex セッションへ修正を依頼する（`/codex:rescue --wait --resume ...`）。誤字・format・明白な一行修正のみ、自分で直してよい。

新しい問題としてやり直すより既存セッションの継続が適切なら、`--resume` で同じスレッドを続ける。

## 差し戻しの上限

修正依頼は2回までを目安にする。2回修正しても合格しない場合は、自分で作業を引き取らず、次をユーザーへ報告する。

- 合格しなかった箇所
- 試した修正
- 解決できなかった理由
- 高性能モデル（`gpt-5.6-sol`）や一段上の推論量（`xhigh`）への切り替えで改善が見込めるか
- 人間の判断が必要な点

## 最終報告

検収を通過したら、次を簡潔に報告する。

- 実装AIが変更した内容
- 選択したモデルと推論量
- 実行した検査
- ディレクターAIが確認した内容
- 残っている制約や未確認事項

モデルの性能は自己評価だけで決めない。実際の差分・テスト・差し戻し回数を判断材料にする。
