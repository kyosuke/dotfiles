# 検収と差し戻し

Codex 完了後に読む。報告だけを信用せず、必ず実際の差分を自分で読む。ペインに見えている記録も証拠にならない（理由と実測は `herdr-execution.md`）。報告と画面が食い違ったら、どちらも信じずに、出力が短くなる形で追試させる。

## 検収の確認項目

`git diff`・`git status` などで実際の変更を読み、次を確認する。

- 要求をすべて満たしているか
- 依頼していない変更が混ざっていないか
- 差分が必要以上に大きくないか
- 既存の設計や技術スタックを尊重しているか
- 不要な依存や抽象化を追加していないか
- 正常系だけでなく失敗時も安全か
- テストが修正内容を本当に検証しているか
- 修正前の壊れた実装でも通るテストになっていないか
- 指定した formatter・lint・型チェック・テストが実際に実行されたか
- 未確認事項を、確認済みであるかのように報告していないか

テストは中身まで読む。「テストが通った」という報告だけでは不十分で、そのテストが今回の変更を検証しているか、壊れた実装を素通しする作りになっていないかを見る。

## テスト件数を数える

テストを追加・変更させたときは、通ったかを見る前に総件数を数える。実運用では、workers プールの起動に失敗して新規4件が1件も走らないまま「完了」と報告された。vitest は起動できたプールの件数（36件）だけを passed として表示するため、要約は成功に見える。

- 発注時に伝えた期待件数と、実際の件数が一致するか確認する。
- プールやプロジェクトを分けている構成では、プールごとの件数を見る。合計だけでは欠落が隠れる。
- 件数を確認するテスト実行はディレクター側で行う。Codex のサンドボックスでは走らない検査がある（`sandbox-network.md`）。

## 移動であって書き換えでないことを確かめる

ファイル分割やモジュール移動を委任したときは、「振る舞いを変えていない」という報告を目で追わない。formatter が移動先で行を再flowするため、`git diff` の行単位比較も行のソート比較も使えない。実測では、oxfmt が三項演算子を1行へ畳み、冗長な括弧を落としたので、純粋な移動でも差分が数百行になった。

宣言単位とリテラル単位で機械的に照合する。スクリプトは `scripts/` にある。どちらも移動前のファイルを `git show HEAD:<path>` で取り出して渡す。

```bash
S=<scratchpad>
git show HEAD:src/foo.ts > $S/old-foo.ts

# トップレベル宣言を名前で突き合わせ、空白を潰して本体を比較する
node ~/.claude/skills/codex-director/scripts/compare-symbols.mjs \
  $S/old-foo.ts src/foo.ts src/foo-a.ts src/foo-b.ts

# テンプレートリテラル（SQL・GraphQL・プロンプト）を多重集合として比較する
node ~/.claude/skills/codex-director/scripts/compare-literals.mjs \
  $S/old-foo.ts -- src/foo.ts src/foo-a.ts src/foo-b.ts
```

`compare-symbols.mjs` は、消えたシンボル・混入したシンボル・本体が変わったシンボルを一覧で返す。

- MISSING と ADDED が空でなければ、そこだけを見る。純粋な移動なら両方とも空になる
- CHANGED は本体を並べて表示する。差分が `export` の付加と formatter の再flowだけなら合格。実測の2ラウンド・3657行の分割では、CHANGED 37件がすべてこの2種類だった
- クラスのメソッドは検出しない。メソッドを自由関数へ変える委任では、この結果を出発点にして該当箇所を手で読む

`compare-literals.mjs` は、外部へ送る文字列が1文字も変わっていないことを示す。GraphQL クエリや SQL の移動では受入の前提に置く。実測では SQL 30本・GraphQL 44本の一致を一発で確認でき、唯一出た差分も `${field}` → `${input.field}` の引数名変更だと即断できた（生成される文字列は同一）。

宣言もリテラルも一致したうえで、構造を変えた箇所（メソッドの自由関数化、関数の分割）だけを手で読む。検収の時間はここへ集中させる。

## テストが本当に欠陥を検出するか確かめる

テストを読むだけでは、それが欠陥を捕まえるかは分からない。実装をわざと壊し、意図したテストだけが落ちることを確認する。実運用ではこの工程が、Codex 自身の検証をすり抜けた穴（テストが存在しない領域の欠陥）を見つけた。

1. 変更されたファイルをスクラッチ領域へコピーしておく
2. 主要な変更につき1つ、破壊的な書き換えを当てる（境界条件の反転、ガード節の削除、条件式の除去など）
3. テストを実行し、落ちたテストが「その変更を検証しているはずのテスト」1件かを見る
4. ファイルを退避から復元し、次の変更へ進む

落ちない変更があれば、その箇所は検証されていない。落ちるテストが多すぎる場合も、テストが変更を特定できていない兆候として扱う。作業後は必ず全ファイルが元に戻り、テストが通る状態に復帰したことを確認する。

**復元は退避したコピーから行う。`git checkout <file>` や `git restore <file>` を使わない。** 検収の時点で Codex の成果物は未コミットなので、これらは壊した1行だけでなく、そのファイルへの成果物全体を HEAD まで巻き戻す。実際に team-activity-observer で `git checkout src/activity-observer/team-digest.ts` を打ち、Codex の変更5箇所を消した（差分を読んだ直後だったため手で復元でき、`git diff` が元の差分と一致することまで確認して復旧した）。手順1のコピーを省いたときは、壊す前に `git diff <file> > <scratchpad>/before.patch` を取ってから壊す。

壊す対象には「層をまたぐ受け渡しの1行」を必ず含める。条件分岐やガード節を壊す検査は素直に落ちるが、値を次の層へ渡すだけの代入は見逃しやすい。実運用では、正規化結果を保存層へ渡す `linkedWorkItemNodeIds: item.linkedItemIds` を `[]` に書き換えても305件が全部通った。新規テスト5件がすべて末端の repository API を直接呼び、フィールドを手渡していたためである。Codex はテストダブルの整備が要る入口からのテストを避けて末端 API を叩きがちで、それでも振る舞いで書いた受入条件は形式上満たせる。発注時は受入条件へ「本番の経路を通ること」を明示し、検収では層をまたぐ代入を1つ選んで壊す。

この工程はディレクター自身が行ってよい。成果物を書き換えるのではなく、検証のために一時的に壊して戻すだけだからである。

## 非コード成果物の場合

上記はコード成果物を前提にしている。文章・ドキュメントなど非コードの成果物には精神を適用する。報告でなく成果物そのものを読み、事実・出典・デモコードの動作を裏取りし、記述が確認済みの事実に基づいているかを見る。技術文章ならデモコードを実際に実行して結果が本文と一致するか確認する。

文章成果物では、節ごとに末尾の段落が新しいことを言っているかを数えて確認する。前段の要約や言い直しが積まれることがある。実測では、2026-08-06の記事2本でそれぞれ2節・3節に発生した。

文体は依頼文で埋まらない領域なので、検収の負荷はここへ寄る。項目の中身より継ぎ目を読む。導入の1文、出典の書き方、地の文の句点、主述のつながりが崩れやすい。textlintのカスタムルールは箇条書き末尾の句点しか見ないため、地の文の句点脱落はここでしか捕まらない。2026-08-11の4件では、事実関係と検査は初回で通り、落ちたのは毎回この層だった。

## 範囲を広げたgrepの検収条件は差分を通読して確かめる

発注時に範囲を広げたgrepを検収条件へ書くと、依頼していない変更が条件を満たしたまま混ざるため、条件の照合だけでは合格に見える。実測では、本番の別経路の表示名が消えており、報告ではなく`git diff`を通しで読んで発見した。

「依頼していない変更が混ざっていないか」は常に確認するが、範囲指定つきの検収条件を出したときは特に見る。消す対象をファイル単位で特定できるなら、そのファイルだけに範囲を絞ったかも確認する。

## 不備を見つけたとき

まず、原因が依頼文の側にないか確認する。完了条件を狭めすぎた依頼文が、正しく動く実装を不合格に見せることがある。その場合は修正依頼ではなく、条件を書き直した発注として出す。

依頼どおりでない不備なら、自分で直さず、問題のあるファイル・挙動・テストを具体的に示して同じ Codex スレッドへ修正を依頼する（同じ名前へ `agent prompt` を送る。手順は `herdr-execution.md`）。誤字・format・明白な一行修正のみ、自分で直してよい。

## 差し戻しの上限

修正依頼は2回までを目安にする。依頼文の不備による出し直しはこの回数に含めない。2回修正しても合格しないなら、自分で作業を引き取らず、次をユーザーへ報告する。

- 合格しなかった箇所
- 試した修正
- 解決できなかった理由
- 高性能モデル（`gpt-5.6-sol`）や一段上の推論量（`xhigh`）への切り替えで改善が見込めるか。`sol` を挙げてよいのは材料が揃っている場合で、読ませる情報を増やして解こうとしているなら収集を分ける側の問題である。切り替えるなら Fast も外す（`-c service_tier=default`。`model-routing.md`）
- 人間の判断が必要な点
