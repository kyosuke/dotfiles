# モデルと推論量の選択

発注設計の前に読む。モデルIDと推論量は、下記の環境確認で実際に判明した値を使う。推測で書き換えない。

## この環境の設定表（検証済み）

| 役割 | モデルID | 選択理由 |
|---|---|---|
| 基本 | `gpt-5.6-luna` | `models_cache.json` で priority 3。推論量を主なつまみにして、定型から高度な実装までこの1モデルで扱う。`~/.codex/config.toml` の既定モデルでもある（2026-08-09 時点で `model_reasoning_effort = "max"`。委任では常に明示して渡すので、この既定には依存しない） |
| 最上位 | `gpt-5.6-sol` | priority 1。`models_cache.json` の説明が "Latest frontier agentic coding model"。絞り込んだ材料から結論を導く場面に限って使う（下記） |

`gpt-5.6-terra`（priority 2）は中間段として置いていたが、実運用でほとんど選ばれなかったので段から外した。`luna` の上限で足りなかったときの扱いは「差し戻しの段」にある。

GPT-5.6 が使えなくなったら、`~/.codex/models_cache.json`（`visibility: list` かつ `supported_in_api: true`）から priority 順に2役を割り当て直し、選んだIDと理由をこの表に反映する。

## 使える推論量（検証済み）

実効レンジは `none, low, medium, high, xhigh, max`。「推論を最小に」は `none` を指す。

- GPT-5.6 の API が受理するのは `none, low, medium, high, xhigh, max` で、**`minimal` は 400（unsupported_value）で拒否される**。`none` は実測で正常に動く。
- 推論量は `herdr agent start` の `--` 以降に `-c model_reasoning_effort=<値>` として渡り、Codex 本体へ直接届く。値を検証して弾く層が間に無いので、Codex が受理する値はそのまま使える（2026-08-05に `luna` + `max` で起動し、TUIのフッター表示と応答を確認）。

`max` は `luna` の最上段として段の並びに入っている（下記）。ただし所要時間と消費が伸びるので既定にはしない。`high` から始めて、難度に応じて上げる。

## Fast モードはモデルで決まる（検証済み）

Fast モードは Codex の `service_tier` である。`models_cache.json` の説明が "1.5x speed, increased usage" で、速度を使用量で買う設定になっている。単価が25倍違うぶん残量の減り方も桁違いなので（下記「コスト差の扱い」）、`luna` では速度を買い、`sol` では買わない。

| モデル | 渡す値 | 意味 |
|---|---|---|
| `luna` | `-c service_tier=priority` | Fast オン |
| `sol` | `-c service_tier=default` | Fast オフ |

推論量と同じく、`herdr agent start` の `--` 以降で毎回明示する。`~/.codex/config.toml` の `service_tier` に任せない。TUI の Fast トグルがこのキーを書き戻すので、ユーザーが対話セッションで切り替えた状態が委任へ漏れてくる。

**値の語彙は [`codex-rs/core/config.schema.json`](https://github.com/openai/codex/blob/main/codex-rs/core/config.schema.json) にある。** `service_tier` の記述は "Optional explicit service tier request id for new turns (for example `default`, `priority`, or `flex`; legacy `fast` also works)"（2026-08-10 参照）。オフを表す `default` はここにしか出てこない。`models_cache.json` は各モデルが対応ティアとして載せている値の表で、GPT-5.6 の4モデルはどれも `priority`（`service_tiers[].id`）と `fast`（`additional_speed_tiers`）だけ。語彙の一覧と取り違えない。

オンに `fast` ではなく `priority` を渡すのは、`fast` がスキーマで legacy とされており、ワイヤ上はどちらも `priority` になるからである。

送られる中身は 2026-08-10 に、ローカルの捕捉サーバーへ `-c model_providers.<名前>.base_url` で向けて実際のリクエスト本文を読んで確認した（`codex exec -m gpt-5.6-luna`）。

| 渡す値 | 送られる `service_tier` | 警告 |
|---|---|---|
| `priority` | `"priority"` | なし |
| `default` | フィールドごと無し | なし |
| `flex` / `standard` / `auto` / `scale` / `none` / 空文字 | フィールドごと無し | あり |
| `false`（真偽値） | 起動しない | `Error loading config.toml: invalid type: boolean` |

対応ティアに無い値でもオフにはなるが、`warning: Configured service tier ... will be omitted from requests.` が毎回ペインに出るので使わない（`flex` はスキーマにあっても4モデルの対応ティアに無く、ここへ落ちる）。警告の有無だけでは、送っていないのかモデル既定の `priority` へ解決されたのかを判別できない。値を変えるときはスキーマで語彙を確かめ、この方法でリクエスト本文まで読む。

## 既定は luna。推論量を主なつまみにする

モデルを先に選ばない。`gpt-5.6-luna` + `high` を基本に置き、難度に応じて推論量を上下させる。実装は `luna` の最上段（`max`）まで使い切ってからでないとモデルを上げない。

| 段 | 指定 | 使う場面 |
|---|---|---|
| 定型 | `luna` + `none` | 変更対象が明示され、実装方法が一意。リネーム、指定された API 変更への追従、既知のパッチ適用、formatter/lint の自動修正、コード生成コマンドの実行、指定した検査コマンドの実行 |
| 単純 | `luna` + `low` | 対象ファイルを探す必要がある。軽い判断を伴う。`none` で一度失敗した |
| 小さめ | `luna` + `medium` | 複数ファイルにまたがるが、設計判断は依頼文で埋まっている。テストの追加位置や境界条件まで指示できている |
| 基本 | `luna` + `high` | 既定。どこから始めるか迷ったらここ |
| やや高度 | `luna` + `xhigh` | 構造の理解が要る、影響範囲が広い |
| 高度 | `luna` + `max` | `xhigh` で合格しなかった。正しさの判定が難しい実装（時刻ずれや有効期間の境界、並行処理、データ移行）や、新規ファイルを含む大きな実装で構成から組ませる場合 |
| 難しい | `sol` + `high` | 実装ではなく、絞り込んだ材料からの判断。下記の条件に当たり、かつユーザーの許可を得たときだけ |

`sol` を `medium` 以下で使わない。`sol` を選ぶ理由は判断の質なので、推論量を下げると噛み合わない。

既定を `luna` にした根拠は試験運用の偏り。19発注が `sol` 7 / `terra` 9 / `luna` 2 で上位偏重、うちログ自身の評価で `sol` 不要が2件。`luna` の2件はどちらも一度で合格した。

## 基本より下げてよいか

依頼文を書き終えた時点で Codex に残る裁量の量で決める。対象ファイルの特定から任せる、実装方針が複数ありうる、境界や基準を決め切れていない、のいずれかが残るなら下げない。ファイル数・行数は段の根拠にしない。実測では `terra` + `medium`（当時は `terra` を中間段に置いていた）が、コード・設定・生成型・仕様書・テストにまたがる7ファイルの移行を、指示していない箇所を grep で見つけて直すところまで一度で通した。軸はコード作業に限らず、調査を伴う文章や検証の要る技術文章も同じ順で判定する。

下げられるかは、依頼文で迷う余地を消せたかで決まる。実測でも、`sol` から `terra` + `medium` へ意図して下げた発注（設計判断を依頼文で全部確定させた5件の修正実装）が差し戻し0で合格し、逆に判定条件を絞りすぎた依頼文が正しい実装を差し戻させた。発注前に次を確認する。

- 設計判断（基準・境界・命名・分割の方針）を依頼文で決め切ったか
- 環境依存の事実（外部 API の応答、DB の制約、既定バージョン）を先に確かめて `<context>` に貼ったか。確かめられない詳細は書かない（`delegation-template.md`）
- 禁止したい文字列や構文にバリアントがあるなら列挙したか。目的の記述は網羅性を保証しない

書けていない状態で段を上げても差し戻しは減らない。書き切れたなら1つ下げて発注し、結果を記録する。

**Codex が検査を実行できないことを段の根拠にしない。** サンドボックスで workers プールや `wrangler dev` が起動しないのは、ペイン起動時のフラグで解消できる環境の設定であって、判断の難度ではない（`sandbox-network.md`）。実行できないまま出して推論量で埋めようとしたことがあるが、ユーザーからその選び方をしないよう指示があった（2026-08-09）。開けられる検査は開けて走らせ、段は依頼文に残る裁量だけで決める。

## luna の射程と限界

実測では `terra` をかなり引き取れている。既定を `luna` にした後の7発注は、`high` 3件と `medium` 2件が差し戻し0、`xhigh` 2件が差し戻し1〜2で、いずれも最終合格した。`high` の射程に入ったのは、新規アダプタの追加、`defineWorkflow` の素関数化、クラスの private メソッド6本の自由関数化、`getWorkItem` の I/O と組み立ての分離。2ラウンド合計3657行を12ファイルへ分割して `tests/` の差分ゼロ、既存シンボルの消失も新規混入もゼロだった。以前なら `sol` を出していた種類の作業である。結果は trial-log に残し続け、段を下げた効果は差し戻し回数と所要時間の両方で見る（推論量を上げれば消費トークンも増える）。

**`medium` 以下では、既存の記述や実装から値を導出する計算を任せない。** 日付・期間・境界・件数が成果物の核になるなら、確定値を依頼文へ書く。実測では、`luna` + `medium` が文書の構成・参照・コード読解を正しく処理しながら、期間計算の日付を1週ずらし、境界も誤った。差し戻しで日付をこちらで確定して渡すと、同じ段で一度で通った。導出そのものが未確定の判断なので、渡さずに投げた時点で段を下げる前提を外している。

**報告の裏取りが甘い。** 既存の分岐が例外を再生成すると報告したが、実際は呼び出しが `try` の外にあり再生成されなかった。コードを読めば分かる内容を推測で書いている（同種の食い違いを `sol` は前の発注で自力で3件見つけていた）。この差は依頼文の `<self_check>`（`delegation-template.md`）と、差分を機械的に照合する検収（`review-checklist.md`）で埋める。格上げでは埋めない。

## sol は許可を取ってから出す

`sol` を使う発注は、毎回ユーザーへ諮ってから出す。読ませる情報量がそのまま消費になり、通読を伴う発注1件で週次のリミットを使い切るからである（2026-08-12、ユーザーからの指示）。

「`sol` を使っていいか」だけを聞かない。判断材料が出ないと答えようがないので、次の3点を添える。

- 何をどれだけ読ませるか。対象と概算量
- `luna` + `max` で足りないと考える理由
- 収集を分ける案を採るなら、その分け方（下記）

情報量の多さそのものは、諮る対象から外す理由にも、`sol` を出す理由にもならない。コードベース全体から問題を見つけるような依頼は、材料が多いまま `sol` の判断力が要る。こうした発注を自分の判断で禁止も実行もせず、分割案と一括案を並べて選んでもらう。

## 収集と判断を分ける

一次資料の通読、広域の grep、ログや差分の走査は、対象と出力形式を指定できるぶん裁量が小さい。`luna` + `low` で足り、対象を列挙できるなら `none` まで下げられる。分担させたいなら収集役を並列に立ててよい（`herdr-execution.md`）。

| 工程 | 段 | 出力 |
|---|---|---|
| 収集 | `luna` + `low`（対象を列挙できるなら `none`） | 見た場所と根拠（`file:line`・URL・引用）を添えた要約。読み取りだけで起動し（`-s read-only`）、報告として返させる |
| 判断 | `sol` + `high` | 収集役の成果を渡し、そこから結論と根拠を出させる |

収集役に原文を転記させない。要約と、確かめるべき箇所へのポインタだけを返させ、判断役には必要ならその箇所を自分で読み直させる。転記を渡すと、`sol` へ一次資料を通読させたのと消費が変わらない。回収できる報告は実測で200行台なので、1件に収まらないなら収集役を分ける（`herdr-execution.md`）。

**収集結果はファイルへ落としてから判断役へ渡す。** 報告の回収をリダイレクトする。

```bash
herdr agent read <収集役> --source recent-unwrapped --lines 600 > <scratchpad>/findings-1.md
```

判断役の依頼文には全文を貼らず、このパスを読ませる。収集役を並列に立てたぶんだけファイルが増えるので、`<context>` にはパスと、各ファイルが何を集めたかの1行を並べる。ディレクターは冒頭と件数だけ確かめ、全文を自分のコンテキストへ通さない。

Codex 側にファイルを書かせないのは、収集役の書き込み権限を開けずに済むからである。`-s read-only` のままなら同じ作業ツリーで並列に走らせられ（`herdr-execution.md`）、収集役が調査のついでに repo を触る余地も残らない。

分けるのが手間なら、一度の発注を `luna` + `max` で出す。段を上げた `luna` は `sol` より桁で安く、収集を含む依頼でも消費が跳ねない。

## sol + high を選ぶ条件

`sol` はほとんどの発注で不要である。既定の段で足りるか、足りないなら `luna` + `max` が先に来る。`sol` を出すのは、材料が絞られたうえで、そこから正しい結論を導くのが難しい場面に限る。

- 集めた材料が食い違い、どれが正しいかを根拠つきで決めさせる
- こちらの仮説を否定してほしい。否定の材料は先に集めて渡す
- 候補が複数残り、選択の根拠まで作らせたい

最大の推論量を常用しない。`sol` + `high` でも不足したときにだけ `xhigh` を検討する。

逆に、次を理由に `sol` を選ばない。実装は難度が高くても `luna` + `max` で出し、落ちた事実を見てから上げる。

- 読ませたい情報が多いだけ。走査・照合・通読そのものは収集の工程で、上の分け方に従う
- ファイル数・行数が多いだけ
- 正しさの判定が難しい実装。`luna` + `max` の段で扱い、境界と基準を依頼文で決め切って検収で捕まえる
- テスト網羅やテスト設計の不足を埋めたい。`sol` + `high` でも「テストが書きにくい設計のまま提出する」「未カバーの分岐を残す」は起きた。必要なテストは依頼文で具体的に指定するか、検収で捕まえる
- 完了誤認や事実と食い違う報告を防ぎたい。workers プールの起動失敗を「完了」と報告した事例は `sol` で起きた。件数を数える、実装を壊して確かめる、といった検収の型で防ぐ領域と混同しない
- 設計判断を丸ごと委ねたい。モデルに設計を任せているだけで、検収の負荷は下がらない

## 差し戻しの段

差し戻しで段を上げるのは既定にしない。実測では、`sol` の初回出力に対する差し戻しが `terra` + `medium` で通り、`terra` の差し戻しが `luna` + `low` で通っている。範囲が限定された時点で必要な判断量は減っている。

- 原因が依頼文の不備 → 同じ段で条件を書き直して出し直す
- 修正範囲が特定のファイル・関数に絞れた → 1つ下げる
- 原因不明のまま2回落ちた → 上げる。`luna` + `max` まで上げても抜けず、材料は揃っているのに結論を誤っているときだけ `sol` を検討する。材料の側が足りないなら、収集を `luna` でやり直す

## コスト差の扱い

推論量の段を単価で選ばない。倍率が効くのはモデルを分ける判断のほうで、そちらでは決め手になる。

2026-07-30 の値下げ後、100万トークンあたりの出力単価は `luna` $1.2 / `terra` $12 / `sol` $30、入力は $0.2 / $2 / $5（[OpenAI の告知](https://openai.com/index/advancing-the-price-performance-frontier-with-gpt-5-6/)。2026-07-31 に確認）。`luna` は `sol` の25分の1で、推論量を `max` まで上げても桁が違う。実装を `luna` の段で押し切る設計はここでも噛み合う。

倍率は入力にも同じだけ効く。読ませた量がそのまま消費へ変わるので、一次資料の通読や広域の走査を `sol` へ出すと、サブスクリプションの週次リミットを1タスクで使い切る（2026-08-12、ユーザーからの指示）。収集を `luna` へ分ける根拠はここにあり、材料を絞ってから `sol` を出せば、同じ判断の質を桁の小さい消費で買える。

ただし発注1件のコストは、差し戻し1回で発生するディレクター側の検収サイクル（差分の読み直し、テストの再実行、追加の依頼文）より小さい。安いから下げるのではなく、依頼文で迷う余地を消せたから下げる。単価は判定の順序を覆さない。

単価は変わる前提で扱う。`models_cache.json` に単価は載っていないので、この節の数値は確認日つきの参考であり、判断に効くほどの差を感じたら出典を引き直す。サブスクリプション経由の実行では、請求は単価ではなくクレジット消費になる。
