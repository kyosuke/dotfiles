# 発注設計

段（モデルと推論量）の選択と依頼文の作り方。発注のたびに読む。モデルIDと設定値は推測せず、下記の出典で確認した値を使う。

## 段の一覧

| 段 | 指定 | 使う場面 |
|---|---|---|
| 定型 | `luna` + `none` | 変更対象が明示され、実装方法が一意。リネーム、指定された API 変更への追従、既知のパッチ適用、formatter/lint の自動修正、コード生成コマンドの実行、指定した検査コマンドの実行 |
| 単純 | `luna` + `low` | 対象ファイルを探す必要がある。軽い判断を伴う。`none` で一度失敗した |
| 小さめ | `luna` + `medium` | 複数ファイルにまたがるが、設計判断は依頼文で埋まっている。テストの追加位置や境界条件まで指示できている |
| 基本 | `luna` + `high` | 既定。どこから始めるか迷ったらここ |
| やや高度 | `luna` + `xhigh` | 構造の理解が要る、影響範囲が広い |
| 高度 | `luna` + `max` | `xhigh` で合格しなかった。正しさの判定が難しい実装（時刻ずれや有効期間の境界、並行処理、データ移行）や、新規ファイルを含む大きな実装で構成から組ませる場合 |
| 難しい | `sol` + `high` | 実装ではなく、絞り込んだ材料からの判断。下記の条件に当たり、かつユーザーの許可を得たときだけ |

`sol` を `medium` 以下で使わない。選ぶ理由は判断の質なので、推論量を下げると噛み合わない。最大の推論量も常用せず、`sol` + `high` で足りなかったときにだけ `xhigh` を検討する。

## モデルと推論量の前提

- `gpt-5.6-luna`（`models_cache.json` で priority 3）を基本に置き、定型から高度な実装までこの1モデルで扱う。`~/.codex/config.toml` の既定モデルでもあるが、委任では常に明示して渡す。
- `gpt-5.6-sol`（priority 1、`models_cache.json` の説明は "Latest frontier agentic coding model"）は、絞り込んだ材料から結論を導く場面に限る。許可制（`../SKILL.md`）。
- `gpt-5.6-terra`（priority 2）は中間段に置いていたが、実運用でほとんど選ばれなかったので段から外した。
- 実効レンジは `none, low, medium, high, xhigh, max`。「推論を最小に」は `none` を指す。**`minimal` は GPT-5.6 の API が 400（unsupported_value）で拒否する。**
- 推論量と `service_tier` は `herdr agent start` の `--` 以降から Codex 本体へ直接届く。値を検証して弾く層が間に無いので、Codex が受理する値はそのまま使える。
- GPT-5.6 が使えなくなったら、`~/.codex/models_cache.json`（`visibility: list` かつ `supported_in_api: true`）から priority 順に2役を割り当て直し、選んだIDと理由をこの節へ反映する。

## Fast モードはモデルで決まる

| モデル | 渡す値 | 意味 |
|---|---|---|
| `luna` | `-c service_tier=priority` | Fast オン |
| `sol` | `-c service_tier=default` | Fast オフ |

Fast は Codex の `service_tier` で、`models_cache.json` の説明が "1.5x speed, increased usage"。速度を使用量で買う設定なので、単価が25倍違う `luna` では買い、`sol` では買わない。

値の語彙は [`codex-rs/core/config.schema.json`](https://github.com/openai/codex/blob/main/codex-rs/core/config.schema.json) にあり、オフを表す `default` はここにしか出てこない（`models_cache.json` は各モデルの対応ティア表で、語彙の一覧ではない）。オンに legacy の `fast` ではなく `priority` を渡す。対応ティアに無い値は警告つきでオフになるだけなので使わない。値を変えるならスキーマで語彙を確かめ、リクエスト本文まで読む（実測とその方法は `evidence.md`）。

## 基本より下げてよいか

依頼文を書き終えた時点で Codex に残る裁量の量で決める。対象ファイルの特定から任せる、実装方針が複数ありうる、境界や基準を決め切れていない、のいずれかが残るなら下げない。ファイル数・行数は段の根拠にしない。軸はコード作業に限らず、調査を伴う文章や検証の要る技術文章も同じ順で判定する。

発注前に3点を確認する。

- 設計判断（基準・境界・命名・分割の方針）を依頼文で決め切ったか
- 環境依存の事実（外部 API の応答、DB の制約、既定バージョン）を先に確かめて `<context>` に貼ったか。確かめられない詳細は書かない（下記）
- 禁止したい文字列や構文にバリアントがあるなら列挙したか。目的の記述は網羅性を保証しない

書けていない状態で段を上げても差し戻しは減らない。書き切れたなら1つ下げて発注し、結果を trial-log へ残す。

**Codex が検査を実行できないことを段の根拠にしない**（2026-08-09、ユーザーからの指示）。サンドボックスで workers プールや `wrangler dev` が起動しないのは、ペイン起動時のフラグで解消できる環境の設定であって、判断の難度ではない（`execution.md`）。開けられる検査は開けて走らせ、段は依頼文に残る裁量だけで決める。

**`medium` 以下では、既存の記述や実装から値を導出する計算を任せない。** 日付・期間・境界・件数が成果物の核になるなら、確定値を依頼文へ書く。導出そのものが未確定の判断なので、渡さずに投げた時点で段を下げる前提を外している。

**`luna` は報告の裏取りが甘い。** コードを読めば分かる内容を推測で書くことがある。この差は下記の `<self_check>` と、差分を機械的に照合する検収（`review.md`）で埋める。格上げでは埋めない。

## sol を選ぶ条件

許可を求める手順は `../SKILL.md`。諮るときは、読ませる対象と概算量、`luna` + `max` で足りない理由、収集を分ける案、週次の残量（起動済みペインへ `/status`。`execution.md`）を添える。

出すのは、材料が絞られたうえで、そこから正しい結論を導くのが難しい場面に限る。

- 集めた材料が食い違い、どれが正しいかを根拠つきで決めさせる
- こちらの仮説を否定してほしい。否定の材料は先に集めて渡す
- 候補が複数残り、選択の根拠まで作らせたい

逆に、次を理由には選ばない。実装は難度が高くても `luna` + `max` で出し、落ちた事実を見てから上げる。

- 読ませたい情報が多い、ファイル数・行数が多い。走査・照合・通読そのものは収集の工程で、下記の分け方に従う
- 正しさの判定が難しい実装。境界と基準を依頼文で決め切って検収で捕まえる
- テスト網羅やテスト設計の不足を埋めたい。`sol` でも未カバーの分岐やテストしにくい設計は残った
- 完了誤認や事実と食い違う報告を防ぎたい。件数を数える、実装を壊して確かめるといった検収の型で防ぐ領域である
- 設計判断を丸ごと委ねたい。検収の負荷は下がらない

情報量の多さそのものは、諮る対象から外す理由にも、`sol` を出す理由にもならない。コードベース全体から問題を見つけるような依頼は、材料が多いまま `sol` の判断力が要る。こうした発注を自分の判断で禁止も実行もせず、分割案と一括案を並べて選んでもらう。

## 収集と判断を分ける

一次資料の通読、広域の grep、ログや差分の走査は、対象と出力形式を指定できるぶん裁量が小さい。分担させたいなら収集役を並列に立ててよい（`execution.md`）。

| 工程 | 段 | 出力 |
|---|---|---|
| 収集 | `luna` + `low`（対象を列挙できるなら `none`） | 見た場所と根拠（`file:line`・URL・引用）を添えた要約。`-s read-only` で起動し、報告として返させる |
| 判断 | `sol` + `high` | 収集役の成果を渡し、そこから結論と根拠を出させる |

収集役に原文を転記させない。要約と、確かめるべき箇所へのポインタだけを返させ、判断役には必要ならその箇所を自分で読み直させる。転記を渡すと、`sol` へ一次資料を通読させたのと消費が変わらない。回収できる報告は実測で200行台なので、1件に収まらないなら収集役を分ける。

**収集結果はファイルへ落としてから判断役へ渡す。** 報告の回収をリダイレクトする。

```bash
herdr agent read <収集役> --source recent-unwrapped --lines 600 > <scratchpad>/findings-1.md
```

判断役の依頼文には全文を貼らず、パスと、各ファイルが何を集めたかの1行を `<context>` へ並べる。ディレクターは冒頭と件数だけ確かめ、全文を自分のコンテキストへ通さない。Codex 側にファイルを書かせないのは、書き込み権限を開けなければ同じ作業ツリーで並列に走らせられるうえ、調査のついでに repo を触る余地も残らないからである。

分けるのが手間なら、一度の発注を `luna` + `max` で出す。段を上げた `luna` は `sol` より桁で安く、収集を含む依頼でも消費が跳ねない。

## 差し戻しの段

差し戻しで段を上げるのは既定にしない。範囲が限定された時点で必要な判断量は減っている。

- 原因が依頼文の不備 → 同じ段で条件を書き直して出し直す
- 修正範囲が特定のファイル・関数に絞れた → 1つ下げる
- 原因不明のまま2回落ちた → 上げる。`luna` + `max` まで上げても抜けず、材料は揃っているのに結論を誤っているときだけ `sol` を検討する。材料の側が足りないなら、収集を `luna` でやり直す

## 依頼文テンプレート

依頼文は、このClaudeとの会話を知らなくても単体で理解できる形にする。Codex もコードベースを探索できるので、不要なファイル全文は貼らない。埋める前に、コードベースを見れば判断できることは自分で調べておく。

```text
<task>
作業の目的と、実施する変更
</task>

<context>
現在の問題、確認済みの事実、関連するファイル
</context>

<constraints>
変更範囲、越えてはいけない境界とその理由、守るべき既存仕様
</constraints>

<acceptance_criteria>
完了と判断できる具体的な条件
</acceptance_criteria>

<verification>
実行するテスト、型チェック、lint など
</verification>

<report>
変更ファイル、実行結果、判断に迷った点、未解決事項
</report>
```

## 意図で書き、禁止の列挙で埋めない

差し戻しのたびに禁止事項を1行足していくと、依頼文は長くなるのに成果物は良くならない。Codex は書かれた字面を満たしながら要点を外し、列挙の外側にある細部が崩れる。公式の推奨も同じ方向で、Anthropic は禁止より要望と背景を書くよう勧め（[Prompting best practices](https://platform.claude.com/docs/en/docs/build-with-claude/prompt-engineering/claude-prompting-best-practices)、2026-08参照）、OpenAI は GPT-5 が矛盾した指示の調停へ推論を費やすと説明している（[GPT-5 prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide)、2026-08参照）。

書き方の順は次のとおり。

1. 何のための作業かを書く。制約には、それが要る理由を1文添える。理由があれば、列挙しなかった場面でも Codex が判断できる。
2. 期待する形は手本で示す。既存のファイル・関数・記事を指し、その粒度に合わせるよう書く。同じ内容を規則へ翻訳し直さない。
3. 判断が要る領域は判断させる。満たすべき振る舞いを渡し、達成の手段は選ばせる。
4. 明示的に塞ぐのは、外れると害が出るものだけにする。

範囲と対象を曖昧にする話ではない。どのファイルか、何を満たせば完了か、どの検査を通すかは具体的に書く。決めないのは達成の手段と出力の形であって、作業の輪郭ではない。

## 報告前の裏取りを依頼文で要求する

次をそのまま `<report>` の直前に置く。Codex は求められなければ、自分の作業を成功した前提で要約する。

```text
<self_check>
報告を書く前に、次を実行する。省略しない。

1. 報告に書こうとしている主張を、実際のコードで確認する。ファイル名と行番号を添える
2. `git diff` を最初から最後まで通しで読む。依頼していない変更が混ざっていないか確認する
3. この依頼文が「保存すべき挙動」として挙げた項目を1つずつ照合し、各項目が満たされている根拠を示す
4. 追加・変更したテストが、変更前の実装でも通ってしまわないか確かめる。通るなら、そのテストは変更を検証していない
5. 確認できていないことを「確認済み」と書かない。未確認は未確認と明示する
</self_check>
```

この節は検収を置き換えない。実装AIが自分では検証しきれない領域（テスト網羅の不足、サンドボックスで走らない検査、完了誤認）は残るので、ディレクター側の検収は同じだけ行う。

## 依頼文へ織り込む前提

この Skill が置いている前提は Codex 側から見えないので、依頼文（主に `<constraints>`）へ理由ごと渡す。

- 変更範囲を目的より広げない。検収では差分を通しで読むため、目的外の変更が混ざると全体が不合格になる。
- 適切な抽象が見えるまで重複を許容してよい。早まった共通化は誤った依存を残すので、重複のほうがましである。
- テストは期待する振る舞いを検証する。修正前の実装でも通るテストは、変更を検証していない。
- テストが書きにくいときは、無理に複雑化せず設計上の問題として報告してよい。ねじれた実装より、その報告のほうが役に立つ。
- 既存の設計・技術スタックを尊重する。この依頼の目的は、そこへ手を入れることではない。

理由を添えずに境界として書くのは次の2つである。外れた時点で害が出るので、判断の余地を残さない。

- コミット・push・デプロイはしない。
- 調査だけを頼むなら「ファイルを変更せず調査のみ」と明記する。実装タスクは既定で書き込み可のため、書かなければ編集される。

## 完了条件は振る舞いで書き、脆い手段だけを塞ぐ

`<acceptance_criteria>` は、目的を満たす実装が複数ありうるなら許容範囲まで書く。判定条件を1つの数値に絞った依頼文が、正しく動く実装を差し戻させたことがある。

例外は、条件を満たす手段の一部が上流の変更に対して脆いときである。エラーメッセージ、識別子、生成物の出力形状のように満たし方が複数ある領域では、Codex は最短の手段を選び、それが脆いほうでも受入条件は全部満たす。「Xに依存するな」と禁止だけを書くと、依存先が別の壊れやすい対象へ移る。根拠にしてよい対象を列挙し、想定される代替の失敗を1つ潰す。「authored な設定ファイル、生成物の JSON、export 文の走査だけを根拠にしてよい」「エラーメッセージの文言を作ってよいのは、それを throw する関数だけ」と書けば、手書きのパーサや文字列置換の余地は消える。列挙できないなら、その検査が成立するかを先に疑う（実例は `evidence.md`）。

## 依頼文の落とし穴

- **`<self_check>` のgrepは対象の場所まで絞る。** 範囲を指定した時点で、その範囲から消す指示になる。消す対象をファイル単位で特定できるなら grep の範囲もそのファイルへ絞り、絞れないなら「この関数のこの分岐から外す」と場所で指定する。範囲を広げたまま出すと、依頼していない箇所まで消えて、しかも条件の照合では合格に見える。
- **型定義だけで実データの形を前提にしない。** 型は「そう扱う」という宣言であって、保存済みデータがその形である保証にならない。`<context>` へ型を貼る前に実データを1件取り出してキーを列挙する。ずれるのは、スキーマが後から厳しくなった、パース層がデフォルト値を補っている、外部APIのレスポンスをそのまま保存している場合。
- **検証できない実装詳細を受入条件に書かない。** サンドボックスの外でしか確かめられない詳細は、Codex が確認できないまま従い、実行段階で落ちる。順は、(1) ディレクター側で確かめられるなら先に実行して結果を `<context>` へ貼る、(2) 確かめられないなら書かず、目的と満たすべき振る舞いだけを渡す、(3) どうしても方針を指定するなら「未検証の想定」と明示し、違っていたら報告させる。
- **検査コマンドは環境で実際に使う形で書く。** サンドボックスで完走するか（ループバックが要るなら起動時に開ける。`execution.md`。開けずに出すなら走る範囲だけを指定し、例: `npx vitest run --project node`、フルスイートはディレクター側で実行すると書く）、check と write のどちらか（`npm run format` が check の環境で Codex が `format:write` へ切り替えた例がある）、テストを追加・変更させるなら期待件数（「既存 N 件 + 新規 M 件で合計 X 件」と示し、報告にも件数を含めさせる。プールの起動失敗でテストが走らないまま成功に見える事故を、この1行で検出できる）。
- **文章成果物では手本を示し、構成を決め切らない。** 分量には下限を書かず、短くなった結果を減点しないと明記する。そのうえで「節末に前段の要約段落を置かない。意味づけの一文だけを置く」は書く価値がある（下限を外すだけでは止まらなかった）。構成は既存の記事を指して節の粒度を読ませ、見出しの文字列・構成要素・項目数までを列挙する形は採らない。枠を増やすと、指定した項目は埋まるのに継ぎ目（導入の1文、出典の書き方、地の文の句点、主述のつながり）が崩れる。文体で落ちても依頼文の指定を増やさず、検収で読んで差し戻す（`review.md`、観測は `evidence.md`）。
