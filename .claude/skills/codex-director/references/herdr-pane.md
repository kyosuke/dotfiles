# herdr のペインで Codex を動かす

既定の委任経路の操作契約。発注の前と、`blocked` が返ったときに読む。この経路を選ぶ理由は、動作がユーザーに見え、承認を求められても復旧でき、差し戻しが同じスレッドで続くことである。2026-08-05に実測して決めた。

herdr 側の操作規約は `herdr --skill`（インストール済みなら `~/.agents/skills/herdr/SKILL.md`、内容は同一）にある。ここに書くのは、それを Codex への委任に当てはめた部分だけである。

## 前提を確認する

```bash
test "${HERDR_ENV:-}" = 1
```

偽なら herdr の外にいる。ペイン経路は使えないので companion 経路へ退避する（`execution.md`）。真なら `herdr` が現在のセッションを操作する。

コマンド構文は入っているバイナリが正典である。この記述と食い違ったら `herdr --help` と `herdr agent` で実際を確認する。

## ペインを用意して起動する

左右に並べる（`--direction right`）。ユーザーの環境は横方向に余裕があり、並べて見るほうが読みやすいという指定である。ユーザーのフォーカスは奪わない。

```bash
herdr pane layout --pane "$HERDR_PANE_ID"
herdr pane split --current --direction right --cwd "$PWD" --no-focus
```

分割後の幅が80桁を下回るなら `--direction down` へ切り替える。80桁は実測の下限で、そこまでは問題ない。ユーザーのタブ（325x98）で既に兄弟ペインがある状態から右へ割ると81桁になり、Codex のTUIは崩れず、237行規模の報告も欠落なく回収できた。単一ペインのタブなら162桁になるので余裕がある。

返った JSON の `.result.pane.pane_id` を使う。IDは予測せず必ず応答から読む。

```bash
herdr agent start <名前> --kind codex --pane <pane_id> --timeout 60000 \
  -- --model <モデルID> -c model_reasoning_effort=<推論量>
```

`--` 以降は Codex のネイティブ引数として渡る。モデルと推論量はここで指定する。名前は `[a-z][a-z0-9_-]{0,31}` で、生きているエージェント間で一意にする。`agent start` は Codex を検知して対話可能になるまで戻らないので、`agent_status` と `interactive_ready` を確認する。

ワークスペース・タブ・worktree は、ユーザーが明示的に求めない限り作らない。同じタブの兄弟ペインと現在の作業ディレクトリを既定にする。

## 発注して完了を待つ

依頼文は Write ツールでファイルへ書いてから渡す。ヒアドキュメントは使わない。理由は2つある。文中のバックティックがコマンド置換として実行される（実運用で `wrangler dev` が起動して残った）。加えて、サンドボックスや権限に触れる文言を含むヒアドキュメントは Claude Code のclassifierに止められることがある。

```bash
herdr agent prompt <名前> "$(cat <scratchpad>/order.txt)" --wait --timeout 300000
```

`--wait` は `idle`・`done`・`blocked` のうち最初に落ち着いた状態で戻る。3つとも1回の呼び出しで受け取れるので、`agent get` を自分でポーリングしない。`--until` は、すでに走っているエージェントが入力を求めるのを待つような状態限定の用途にだけ使う。

戻った `agent_status` で分岐する。

| 返り値 | 意味 | 次の動作 |
|---|---|---|
| `idle` | 完了して入力待ち | 報告を回収して検収へ進む |
| `done` | 未見のまま完了 | 同じ。`idle` と同一の状態で、タブが見られていないだけ |
| `blocked` | 承認か質問のUIが出ている | 下記「承認を求められたとき」へ |

`idle` と `done` を区別して扱わない。同じタブの兄弟ペインなら `idle` が返るが、タブが見られていなければ `done` になる。どちらも完了である。

実測した所要時間は、読み取りだけの小さな依頼で12〜40秒だった。実装を伴う依頼は20分を超えることがある。Bashツールの上限は10分なので、長い依頼は `run_in_background: true` で投げ、完了通知を受けてから読む。

`unknown` は完了の証明にならない。Codex がいるが分類できていない状態である。

## 報告を回収する

```bash
herdr agent read <名前> --source recent-unwrapped --lines 600
```

実測では237行・見出し36件の報告を `--lines 600` で欠落なく回収できた。81桁のペインでも213行を全項目そろって回収できたので、幅は回収の精度に影響しない（`recent-unwrapped` がソフトラップを繋ぎ直す）。

**終端マーカーを依頼文に入れない。** 完了の検知は herdr の仕事で、`--wait` が状態として返す。依頼文に `REPORT-END` のような終端行を出させても、その判定は二重になるだけである。

取りこぼしの検出にも使えない。読み取りは常に下端を基準にするので、失われるのは先頭である（実測: 500行の出力を `--lines 10` で読むと 493〜500 が返り、1〜10 は返らない）。終端マーカーは、報告の冒頭が切れている状態でも必ず読める。検出したい失敗をすり抜ける。

**`recent` 系が0行で返ることを失敗と読まない。** 出力がまだ画面に収まっている間はホストのスクロールバックが空なので、`recent` と `recent-unwrapped` は終了コード0で何も返さない。実測では、短い応答のあと両方が0行を返す一方で `visible` と `detection` は正しく読めた。同じペインで長い報告を出させたあとは `recent-unwrapped` が213行を返した。

読み取り源は用途で選ぶ。

| 源 | 用途 |
|---|---|
| `recent-unwrapped` | 画面を超えた長い報告・ログ。ソフトラップを繋ぐ |
| `visible` | 画面に収まっている応答。`recent` 系が空のときの退避先 |
| `detection` | 承認UIの選択肢 |

報告が全部読めているかは、`--lines` を増やして内容が増えるかで見る。増えないのに報告の冒頭（依頼文のエコーや報告の先頭）が見えないなら、Codex が代替画面に描いていて行が失われている。そのときだけ、報告をMarkdownでファイルへ書いてファイルパスだけを返すよう依頼し直し、ファイルを読む。最初の依頼文でファイル出力を求めない。

機械的に判定したい場合は、マーカーを報告の**先頭**に置く。失われるのは先頭なので、そこに置いたマーカーが読めれば全体が読めている。

## ペインの記録は証拠ではない

ペインに見えるのは Codex が描いた画面であり、コマンドの生出力ではない。Codex はツール出力を `… +464 lines` のように畳んで表示する。畳まれた部分は読めない。

これは実害を出した。listen の可否を調べさせたとき、最終報告は `EPERM` と書いていたが、画面に見えていたのは `TIMEOUT` と `SERVER_CLOSED` だった。畳まれた行に本当の出力があった。追試すると `EPERM` が事実で、`TIMEOUT` は Codex 自身のスクリプトに残ったタイマーの出力だった。報告と画面が食い違ったら、どちらも信じずに、出力が短くなる形で追試させる。

検収は画面ではなく `git diff` で行う（`review-checklist.md`）。

## 承認を求められたとき

`blocked` が返ったら、まず状況を読む。

```bash
herdr agent get <名前>
herdr agent read <名前> --source detection --lines 30
```

ここに境界がある。**ディレクターは承認を代行しない。** Claude Code のclassifierが `send-keys` による承認の代理入力を止める。実際に止められた操作は3つある。

- Codex へ「サンドボックス外への権限昇格を要求して」と指示する発注
- Codex の承認プロンプトへ `send-keys y` で承認を入力する操作
- 権限昇格の文言を含むヒアドキュメント

却下は通る。`herdr agent send-keys <名前> esc` で却下でき、実測ではファイルは作られなかった。

したがって承認が必要な場面は、見えているペインでユーザーが押す。ディレクターは何の承認を求められているかをユーザーへ伝えて待つ。ペイン経路は動作が見えるので、この運用が噛み合う。

却下した直後は Codex が「どうするか指示して」で待つため、`agent_status` は `blocked` のままである。通常の `agent prompt` を送ると `idle` に戻る。

承認方針を Codex 側で厳しくしても運用は改善しない。`-a untrusted` で起動すると `find` のような読み取りコマンドにも承認が要る。ディレクターは承認できないので、そのペインでは作業が進まない。既定の `on-request` のまま起動する。

## 差し戻す

同じ名前へ `agent prompt` を送るだけで同じスレッドが続く。companion 経路の `--resume-last` にあたる操作は要らない。実測では前のターンの内容（「先ほど要約した5ファイル」）を理解して続けた。

送る前に `agent_status` が `idle` か `done` であることを確認する。`blocked` のまま送ると、返ってきた `blocked` が新しい承認か直前の承認かを区別できない。`state_change_seq` が進んだかで判定する。

## スレッドIDと後片付け

`agent_session.value` が Codex のセッションIDである。`/quit` 時に Codex が表示する `codex resume <UUID>` と一致する。ペインを閉じたあとでも同じスレッドへ戻れるので、長い作業では記録しておく。

作業が終わったら Codex を終了させ、自分が作ったペインだけを閉じる。

```bash
herdr agent prompt <名前> "/quit"
herdr pane close <pane_id>
```

自分が作っていないワークスペース・タブ・ペイン・セッションは、ユーザーが明示的に求めない限り閉じない。`herdr server stop` は使わない。

## 並列化

同じ作業ツリーで複数の Codex 実装を並列に走らせない。並列化するなら worktree を分ける。ペインを分けても作業ツリーは共有されるので、ペインの分離は並列化の根拠にならない。
