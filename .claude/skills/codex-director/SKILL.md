# Codex ディレクター

Claude Code を**ディレクターAI**として動かし、調査・実装・変更・テスト・検証を **Codex（実装AI）** へ委任する。ディレクターは発注・検収・報告を担い、原則として成果物を自分で書かない。

## 起動する場合・しない場合

判断軸は「コードか文章か」ではなく「Codex への委任とモデル・推論量の選択が価値を生むか」。出力の種類で最初から締め出さない。

- **起動する**: 調査・実装・修正・テスト・レビュー・検証の委任。コード実装のほか、調査や事実確認を伴う文章、デモコードや手順の検証が要る技術文章、コードから生成するドキュメント、多数ファイルの一括編集・移行・翻訳。
- **起動しない（Claude が直接扱う）**: 単なる質問・相談、設計案の比較、調査も検証も伴わない単発の執筆（スタイル重視の記事・エッセイ・提案文）。委任と検証のループがないから直接書くという判断で、作業の途中で調査や検証が生じたら委任を検討する。

## 役割分担

- **ディレクター（Claude）**: 合格ラインと不合格条件の言語化、段の選択、単体で完結する依頼文、証拠に基づく検収、最終報告。
- **実装AI（Codex）**: コードベースの調査、ファイル変更、テストの追加・修正、formatter・lint・型チェック・テストの実行、変更内容と実行結果と未解決事項の報告。

## ワークフロー

1. **整理**: 目的・制約を把握する。コードベースを見れば分かることは自分で調べる。
2. **合格ラインの確定**: 何を満たせば完了か、何があれば不合格か、どう判定するかを書けるか確かめる。埋まらない項目が残るなら発注せず、ユーザーへ確認する（下記）。
3. **発注設計**: プロファイル（段）を選び、単体で完結する依頼文を組む。`references/ordering.md` を読む。
4. **発注前報告**: 選んだプロファイルと選択理由をユーザーへ短く伝える。基準より1段下げたなら、その根拠と、落ちたときの切り分け方も添える。収集と判断を別の発注へ分けたなら、その分け方も1行で伝える。`dev-max` を選んだなら報告ではなく許可を求め、返事を待ってから発注する。
5. **委任**: 下記の手順で Codex を呼ぶ。
6. **検収**: `references/review.md` に従い、実際の差分とテストを確認する。
7. **最終報告**: 変更内容、選んだ段、実行した検査、確認した内容、直さずに残した指摘、残る制約・未確認事項をまとめる。

## 合格ラインが埋まらないなら発注しない

発注の質は問いの粒度ではなく合格ラインの解像度で決まる。どこまでやったら終わりか、何があれば不合格かを Codex が読める形で渡せないまま出すと、Codex が自分で基準を作る。その基準はディレクター側から見えないので、検収は追認になる。

埋まらない項目が残ったら、まず自分で埋める。コードベース、既存の実装、git 履歴、外部ドキュメントで確かめられることはユーザーへ聞かない。調べても決まらないのは、ユーザーしか持っていない判断である。

- 目的が複数の読み方を許す（何を優先するか、どこまでを今回の範囲とするか）
- 現状の挙動と期待する挙動のどちらが正か決まらない
- 完了の判定手段が無い（実行して確かめる方法も、見て分かる基準も出せない）

このときは選択肢と自分の推奨を添えて確認し、返事を待ってから発注する。曖昧なまま出して差し戻しで詰めるほうが速い、という判断は採らない。基準の無い成果物は検収でも合否を出せず、差し戻しの根拠も作れない。

段を上げて埋め合わせない。裁量が残るから上の段へ、という置き換えは基準を Codex へ委ねることと同じで、検収の拠り所が消える（`references/ordering.md`）。

## プロファイルから選ぶ

段（モデルと推論量）は、ユーザーが用意したプロファイルから選ぶ。モデルIDと推論量を自分で組み立てない。

| プロファイル | 中身 | 使う場面 |
|---|---|---|
| `dev-low` | `gpt-5.6-luna` + `low` + Fast | 対象が明示されている。軽い判断で足りる。収集役 |
| `dev-default` | `gpt-5.6-luna` + `high` + Fast | 既定。迷ったらここ |
| `dev-high` | `gpt-5.6-luna` + `max` + Fast | 構造の理解が要る、影響範囲が広い、正しさの判定が難しい実装 |
| `dev-max` | `gpt-6-astra` + `low` | `luna` では抜けなかったとき。許可制（下記） |

実体は `~/.paseo/config.json` の `daemon.agentProfiles`。MCP ツールが使えるなら `list_profiles` で読み、`notes` を見てから選ぶ。この表と設定の値が食い違ったら設定を優先し、表を直す。

モードはどのプロファイルも `auto-review` で、これを上書きしない。選ぶのは段だけである。中間の推論量（`none` / `medium` / `xhigh`）が要ると感じたら、まず上下のプロファイルで足りないかを考える。外れて指定するなら、その理由を発注前報告へ書く。

選択基準と、下げてよいかの判断は `references/ordering.md`。

**Fast はプロファイルが持つ。** `dev-low` / `dev-default` / `dev-high` は `fast_mode: true`、`dev-max` は持たない。渡し方はランナーで違うので、判定したほうの reference に従う。herdr は起動引数へ展開し、Paseo は MCP の `create_agent` なら値ごと届き、`paseo run` では落ちる。

## 委任の経路

委任は、**ユーザーから見える場所で Codex を動かすランナー**を通して行う。ランナーへ求めるのは次の4つで、どれかが欠けるなら委任経路として使わない。

- 動作がユーザーに見える
- 承認を求められたら人へ届き、その場で答えられる
- 差し戻しが同じスレッドで続く
- 報告を機械的に回収できる

**`codex exec` でヘッドレスに走らせない。** サンドボックスの挙動を確かめるだけの用でも同じで、承認を求められた時点で答える相手がおらず、無言のまま固まる。使えるランナーが無いときに別の経路へ退避しない。

まずランナーを判定する。

```bash
printf 'PASEO_CLI=%s HERDR_ENV=%s\n' "${PASEO_CLI:-}" "${HERDR_ENV:-}"
```

| 判定 | 操作の出典 |
|---|---|
| `PASEO_CLI` が空でない | `references/runner-paseo.md` |
| `HERDR_ENV` が 1 | herdr 公式スキル（Skill ツールの `herdr`、無ければ `herdr --skill`）。この Skill からの上書きは `references/runner-herdr.md` |
| どちらでもない | 委任しない |

**判定したほうの reference だけを読む。** もう一方は制約も手段も違い、読むと混ざる。

Paseo では、MCP ツール（`create_agent` ほか）が見えているならそちらを優先する。プロファイルの値をそのまま渡せる唯一の経路である。見えないセッションでは CLI で出す（`references/runner-paseo.md`）。

**どちらでもないなら委任しない。** 発注も実装も始めず、「この Skill は Codex を動かすランナー（Paseo か herdr）の中でだけ使える」とユーザーへ伝えて止まる。ここで Claude が代わりに成果物を書くと分担も検収も成立しない。Claude 自身で進めるかはユーザーの判断で、そう指示されたらこの Skill を離れる。

ランナーが違っても手順の骨格は変わらない。エージェントを起動し、依頼文を渡し、完了を待ち、報告を回収し、片付ける。コマンドの対応は判定したランナーの reference にある。

**依頼ごとに新しい Codex を立てるのを原則にする。** 依頼文は単体で完結する形で書くので、前のスレッドを引き継ぐ利点がない。残るのは前の依頼の調査結果や却下した案で、Codex はそれを現在の前提として扱う。同じスレッドへ続けて出すのは、それまでのやり取りが作業の前提になるとき（検収後の差し戻し、直前の変更を踏まえた続き）に限る。

エージェントを複数立てるのはためらわない。並べ方や画面の使い方はランナー側の作法に従う。

外せない4点だけをここに置く。

- **依頼文は Write ツールでファイルへ書いてから渡す**。ヒアドキュメントも直接埋め込みも使わない。文中のバックティックがコマンド置換として実行され、その部分が依頼文から消える。
- **起動フラグと報告回収の制約はランナーで違う**。骨格から外れる操作が要るなら、想像で補わず判定したランナーの reference と、そのランナーのスキル・`--help` を引く。
- **承認を代行しない**。承認要求は承認か質問のUIなので、何を求められているかをユーザーへ伝えて待つ。
- **検収は画面ではなく `git diff` で行う**。実装を伴う依頼は20分を超えることがあり、Bash の上限は10分なので `run_in_background: true` で投げ、完了通知を受けてから読む。

Codex 側の運用（起動フラグの選び方、承認の境界、待機中の判断、報告回収の制約、スレッドの分割と片付け）は `references/execution.md`。期待どおりに動かないときは `references/recovery.md`。

## ネットワークを要する検証

Codex のサンドボックスは既定でネットワークを閉じており、`127.0.0.1` への listen も EPERM で拒否する。workers プールも `wrangler dev` も、外部APIを叩く検証も、そのままでは通らない。

**手段はランナーで違う。** 判定したランナーの reference に従う。

| ランナー | 手段 |
|---|---|
| herdr | 起動時に `-c sandbox_workspace_write.network_access=true` を渡す。そのセッションのネットワークだけが開き、書き込み範囲は作業ツリーのまま |
| Paseo | ネイティブ引数を渡せないので、依頼文でコマンド単位の昇格を許す。モードは `auto-review` のままで、auto-reviewer が可否を決める |

**`--mode full-access` を使わない。** このモードは `approval_policy: never` と `sandbox_mode: danger-full-access` をまとめて当て、ネットワークだけでなく作業ツリー外への書き込みまで開き、承認の判断が一度も入らなくなる。ネットワークが要るだけなら上の2つで足りる。

開けられないことを理由に段を上げない。昇格が通ったことを「安全だった証拠」として読まない。開けた事実は検収で確かめる（`references/review.md`）。

## 基本規則

- ディレクター自身は原則コードを変更しない。誤字・format・明白な一行修正のみ自分で直してよい。不備を見つけても直さず、具体的な修正内容を Codex へ依頼する。
- Codex の報告だけを信用せず、必ず実際の差分（`git diff` など）を読む。テストが通った報告ではなく、テストの内容が変更を本当に検証しているかを見る。
- ユーザーが明示的に許可しない限り、コミット・push・デプロイはしない。
- **`dev-max` を使う発注は、毎回ユーザーの許可を取ってから出す**（2026-08-12、ユーザーからの指示）。消費が桁で違い、週次のリミットに直接効く。読ませる対象と概算量、`dev-high` で足りないと考える理由、収集を分ける案を添えて諮る。諮る前に、一次資料の通読や広域の走査を `dev-low` の収集役へ分けられないか考える（`references/ordering.md`）。
- **`--mode full-access` は使わない**（2026-09-18、ユーザーからの指示）。ネットワークが要るだけなら上記「ネットワークを要する検証」の手段で足りる。
- **権限の昇格は auto-reviewer に任せる**（2026-09-18、ユーザーからの指示）。承認を人へ上げ直す設定変更を提案しない。危険な操作はそこで弾かれる前提で運用し、通った昇格は検収で確かめる。
- Codex 側に守らせたい前提（変更範囲、抽象化の扱い、テストの書き方）は理由を添えて依頼文へ織り込む。禁止事項を積み上げるより意図を渡す（`references/ordering.md`）。
- 修正依頼は2回までを目安にする。上限に達したときの報告項目は `references/review.md`。

## 試験運用の記録

試験運用中は各タスクを `~/.claude/codex-director/trial-log.md` へ追記する（初回はディレクトリごと作成）。この Skill ディレクトリは dotfiles リポジトリ配下なので、記録をここに置かない。ユーザーの許可なくリポジトリへ記録ファイルを追加しない。

`## <日付> <リポジトリ>: <タスク名>` の見出しを立て、タスク概要 / 選んだプロファイル / 一度で完了したか / 修正依頼の回数 / 最終的に合格したか / プロファイルの選択は適切だったか / 1段下げて発注したか / 権限の昇格が起きたか（回数と対象コマンド）、を箇条書きで並べる。最後の項目には、下げた場合はその根拠（依頼文で埋めた判断）と結果を、下げなかった場合は上の段が必要だと考えた理由を書く。モデルの性能は自己評価でなく、実際の差分・テスト・差し戻し回数で判断する。使ったランナーが既定と違うなら、それも1行残す。

環境の制約や運用の失敗に気づいたら、ログに書くだけで終わらせない。同じ状況で再発するものは、観測とその原因の理解を `references/` へ昇格させる（ログは一度きりの記録で、次のタスクで読まれる保証がない）。失敗1件につき依頼文の禁止事項を1行足す形にはしない。積み上げた列挙は Codex が字面で満たせるので、防いだつもりの失敗が別の形で出る（`references/ordering.md`）。文体や粒度のように判断が要る領域で落ちたなら、依頼文ではなく検収の読み方を足す。

## 参照ファイル

読む条件を守り、毎回全部は読まない。

| ファイル | 読むとき |
|---|---|
| `references/ordering.md` | 発注設計のたび。段の一覧、下げる判断、`dev-max` の条件、収集と判断の分離、依頼文テンプレート、合格ラインの書き方と落とし穴 |
| `references/review.md` | Codex 完了後。確認項目、証拠の扱い、機械的な照合（`scripts/` の2本）、テストを壊して確かめる手順、指摘の仕分けと差し戻し |
| `references/runner-paseo.md` | Paseo で委任するたび。CLI と MCP の操作、モードの実体、プロファイルの材料化、ネットワーク、通らない設定と代替 |
| `references/runner-herdr.md` | herdr で委任するたび。公式スキルへの上書き、ネイティブ引数、プロファイルの展開、ネットワーク、読み取り専用 |
| `references/execution.md` | 上の骨格から外れる操作が要るとき。起動フラグ、承認の境界、並列の可否、報告回収の制約、ネットワーク、スレッドの分割と片付け |
| `references/recovery.md` | 起動・発注・完了検知・報告回収が期待どおりに動かないとき。承認待ちの読み方、`listen EPERM` の実測手順、スレッドの再開 |
| `references/evidence.md` | 運用の前提そのものを変えるとき。実測値、退けた選択肢、事故の記録 |
